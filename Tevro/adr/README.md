# Tevro — 착수 전 결정 기록(ADR)

- 문서 상태: 색인. ADR-0001과 ADR-0002는 채택(Accepted, 2026-10-08)했고, 나머지 ADR은 제안(Proposed) 상태이며 채택된 결정이 아니다.
- 작성일: 2026-10-07
- 개정: 2026-10-07 공정 계층 요구 반영
- 개정: 2026-10-08 ADR-0001 채택 반영
- 개정: 2026-10-08 ADR-0002 채택 반영
- 관련 문서: [해결하려는 문제와 제품 요구사항](../product-requirements.md), [활용 가능한 오픈소스와 구현 경계](../open-source-components.md)
- 목적: 초기 핵심(PRD §11) 구현에 착수하기 전에 정해야 할 기술·계약 결정을 한곳에 모으고, 결정 순서와 확인할 환경 사실을 공유한다.

> 프로젝트 담당자는 2026-10-08에 ADR-0001(서버·웹·CLI 기술 구성)과 ADR-0002(폐쇄망 배포 형태와 반입 경로)를 채택했다. 나머지 ADR은 아직 채택하지 않았고, 각 ADR의 '제안하는 결정'은 검토를 위한 제안이다.

## 1. 상태 정의

| 상태 | 뜻 |
| --- | --- |
| 제안 (Proposed) | 검토 중이다. 구현의 근거로 삼지 않는다 |
| 채택 (Accepted) | 결정권자가 확인했다. 구현의 근거가 된다 |
| 기각 (Rejected) | 검토 후 채택하지 않았다. 이유를 문서에 남긴다 |
| 대체 (Superseded) | 다른 ADR이 이 결정을 바꿨다. 대체한 ADR 번호를 적는다 |

상태는 '제안 → 채택', '제안 → 기각', '채택 → 대체' 방향으로만 바뀐다. 채택한 ADR의 내용을 바꾸려면 새 ADR을 쓰고 기존 ADR을 대체 상태로 둔다.

## 2. 채택 절차

1. 프로젝트 담당자가 ADR마다 결정권자를 지정한다.
2. 각 ADR의 '채택 전 확인할 사항'을 확인해 결과를 ADR에 적는다. 추측으로 채우지 않는다.
3. 결정권자가 선택지를 확인한다. 제안과 다른 선택지를 고르면 '제안하는 결정'을 고쳐 쓴다.
4. 상태를 채택 또는 기각으로 바꾸고, 결정일과 결정권자를 적는다. 고르지 않은 선택지와 이유는 지우지 않는다.
5. PRD §13의 해당 항목을 결정 결과로 갱신한다. OSS에 관련 내용이 있으면 함께 갱신한다.
6. '후속 작업' 체크리스트를 작업 항목으로 옮긴다.

## 4. 결정 순서(크리티컬 패스)

```text
0001 → 0002 → 0003 → (0004, 0005 병렬) → 0006 → 0007
```

| 순서 | ADR | 이 위치에 두는 이유 |
| --- | --- | --- |
| 1 | 0001 기술 구성 — 완료(2026-10-08 채택) | 언어·런타임이 정해져야 검증 위치, 계약 공유 방식, 반입 런타임 수가 정해진다 |
| 2 | 0002 배포 형태 — 완료(2026-10-08 채택) | 저장소 선택이 배포 대상(컨테이너 플랫폼, 볼륨 종류, 사내 DB)에 묶인다. 반입 승인 리드타임이 가장 길 수 있다(사내 절차 확인 필요) |
| 3 | 0003 저장소·동시성 | 트랜잭션 경계와 충돌 모델이 없으면 API의 쓰기 의미와 충돌 오류를 정할 수 없다 |
| 4 | 0004 인증·권한 | 모든 API의 미들웨어와 권한 오류의 의미를 정한다. 0005와 서로 참조하지만(ID 접두사, 관리자 권한) 어느 쪽이 먼저 정해져도 된다 |
| 4 | 0005 식별자·삭제 | 첫 테이블과 첫 CLI 명령의 식별자 계약이다. 0004와 서로 참조하지만(ID 접두사, 관리자 권한) 어느 쪽이 먼저 정해져도 된다 |
| 5 | 0006 API 계약 | 앞의 결정(충돌, 권한, 식별자)을 모아 GUI와 CLI가 공유할 계약으로 만든다 |
| 6 | 0007 CLI 계약 | 0006의 오류 코드가 정해지면 종료 코드와 출력 스키마를 바로 확정할 수 있다 |

후속 ADR 후보(§8)는 0005·0006의 골격이 나오면 병행해서 결정한다.

## 5. ADR 사이의 공통 용어

모든 ADR이 같은 이름을 쓴다.

| 용어 | 뜻 | 정의한 곳 |
| --- | --- | --- |
| `graph_revision` | 프로젝트 구조(공정 생성·삭제, 상위 변경, 종속성 추가·삭제)가 바뀔 때마다 1 오르는 정수. API 필드 `graphRevision`, 기대값 `expectedGraphRevision`, CLI `--expected-revision` | ADR-0003 |
| `version` | 공정 필드(제목, 설명, 실행 상태, 선택 정보)가 바뀔 때마다 1 오르는 공정별 정수. HTTP `If-Match`, 기대값 `expectedVersion`, CLI `--expected-version` | ADR-0003 |
| 변경 묶음(change set) | 공정 생성(임시 ID)·수정·삭제, 상위 변경(`task.move`), 종속성 추가·삭제를 한 요청에 담아, 최종 상태를 한 번 검증하고 원자적으로 적용하는 단위. `dryRun` 지원 | ADR-0006 |
| ID 접두사 | `prj_` 프로젝트, `tsk_` 공정, `dep_` 종속성, `tpl_` 템플릿, `ttk_` 템플릿 공정, `usr_` 사용자, `tok_` 토큰 식별자, `tmp_` 변경 묶음 안 임시 ID | ADR-0005 |
| 오류 코드 → 종료 코드 | `VALIDATION_*`·`REFERENCE_NOT_FOUND`·`CROSS_PROJECT_REFERENCE`·`HIERARCHY_CYCLE`·`CROSS_LEVEL_DEPENDENCY`·`HAS_DEPENDENCIES` → 3, `UNAUTHENTICATED`·`FORBIDDEN` → 4, `CONFLICT` → 5, `NOT_FOUND` → 6, `EXTERNAL_INTEGRATION_FAILED` → 7(예약), CLI 사용법 오류 → 2, `INTERNAL`·`CLIENT_VERSION_UNSUPPORTED`·기타 → 1, 성공 → 0 | ADR-0006, ADR-0007 |
| `parent_id`(상위 공정 ID) | 공정이 속한 상위 공정의 ID. 선택이며 없으면 최상위 공정이다. 같은 프로젝트의 공정만 가리키고, 공정은 상위를 최대 하나 가진다(트리). 종속성 데이터에 섞지 않는다. API 필드 `parentId`(최상위면 `null`), 변경 묶음 작업 `task.create`의 `parentId`와 `task.move`, CLI `--parent` | ADR-0003, PRD §6.9 F-H01 |
| 층(level) | 같은 상위를 가진 형제 공정의 집합. 최상위 공정들(`parent_id` 없음)도 한 층이다. 선행관계는 같은 층 안에서만 맺고, 순환 검사도 층마다 따로 한다(F-H03) | ADR-0003, ADR-0006 |
| 말단 공정 | 하위 공정이 없는 공정. 상태 요약(F-S05)은 말단 공정 기준으로 센다(F-H09) | PRD §6.9 F-H09 |
| `childCount`, `doneChildCount` | 직접 하위 공정 수와 그중 완료 수. 저장하지 않고 조회 시 계산한다. 공정 조회 응답과 CLI `--json`에 포함한다 | ADR-0006, ADR-0007 |
| `prerequisites.inherited`, `inheritedFrom` | 조상에 맺힌 선행관계에서 상속된 선행 공정 목록과, 각 항목이 어느 조상에서 왔는지를 담는 필드. 직접 선행은 `prerequisites.direct`(F-H04) | ADR-0006 |
| `autoTransitions` | 실행 상태 변경 응답에 담는, 자동으로 완료된 상위 공정 목록. 각 항목은 `{taskId, status, version, cause}`(F-H05) | ADR-0006, ADR-0007 |
| `HIERARCHY_CYCLE` | 자기 자신이나 자손을 상위로 지정하는 변경(F-H02, AC-29). 종료 코드 3 | ADR-0006 |
| `CROSS_LEVEL_DEPENDENCY` | 다른 층의 공정 사이에 선행관계를 맺는 변경(F-H03, AC-27). 종료 코드 3 | ADR-0006 |
| `HAS_DEPENDENCIES` | 선행·후속 연결이 남아 있는 공정의 상위를 바꾸려는 변경(F-H08, AC-32). 같은 변경 묶음 안에서 연결을 먼저 지우면 통과한다. 종료 코드 3 | ADR-0006 |

상위로 지정한 공정이 없으면 `REFERENCE_NOT_FOUND`, 다른 프로젝트의 공정이면 `CROSS_PROJECT_REFERENCE`다. 계층 전용 '상위 없음' 코드는 두지 않는다.

## 6. 착수 전 확인할 환경 사실

추측으로 채우지 않고 사내 담당자에게 확인한다.

| 항목 | 영향받는 ADR | 확인 대상 |
| --- | --- | --- |
| 내부 npm 레지스트리(미러) 유무와 개발 PC 접근 가능 여부 — 확인됨(2026-10-08): 있음 | 0001, 0002, 0007 | 사내 인프라 담당 |
| 내부 OCI 레지스트리 유무 | 0002 | 사내 인프라 담당 |
| OpenShift·컨테이너 런타임 사용 가능 여부와 필수 여부, 영속 볼륨 종류 — 미확인. ADR-0002는 B로 채택했고 컨테이너 이전 여지를 남겼다 | 0002, 0003 | 사내 플랫폼 담당 |
| 사내 운영 DB(PostgreSQL) 서비스 유무 — 확인됨(2026-10-08): 쓸 수 없음 | 0002, 0003 | 사내 DB 담당 |
| 사내 CA 번들의 위치·형식과 OS 신뢰 저장소 설치 여부 | 0002, 0007 | 사내 보안·인프라 담당 |
| 사내 LDAP/AD, SSO, 망 내 OIDC 제공 여부 | 0004 | 사내 인증·보안 담당 |
| 기밀 프로젝트 열람 제한이 필요한지 | 0004 | 프로젝트 담당자, 이해관계자 |
| CLI 실행 호스트(개발자 PC, 에이전트 실행 환경)의 OS와 Node.js 유무·버전 | 0001, 0007 | 개발 참여자, 에이전트 사용 담당 |
| 사내 Jira 업그레이드·이전 계획, 망 내 접근 경로, 서비스 계정 | 0001, 0004(연계) | 사내 Jira 관리자 |

사내 Jira 9.15는 2026-03-27에 지원이 끝났고 Jira Data Center 제품군은 2029-03-28 EOL 이후 읽기 전용이 된다(PRD §6.7 '대상 Jira 환경'). Jira는 4단계 선택 연동이라 초기 핵심 착수를 막지는 않지만, 업그레이드 계획은 Jira 어댑터와 SDK 판단(ADR-0001)에 영향을 준다.

## 8. 후속 ADR 후보

ADR로 아직 쓰지 않았다. 0005·0006의 골격이 나오면 병행해서 결정한다.

| 후보 | 요약 | PRD 관련 |
| --- | --- | --- |
| 실행 상태·선행 조건 판정 모델 | 실행 상태는 세 값으로 두고 '확인 필요'는 별도 표시로 다루는 PRD §6.4의 해석을 데이터·API로 옮긴다. 선행 조건 판정을 충족·미충족·판정 불가로 서버가 계산해 응답에 넣을지, 직접 선행 기준 판정과 전이적 모순의 비차단 경고를 어떻게 줄지 정한다. 계층 자동 전이의 세부(PRD §13-16)도 여기에 포함한다: 하위 하나라도 착수하면 상위를 진행 중으로 자동 변경할지(제안: 예), 자동 완료된 상위의 하위를 다시 열면 상위를 되돌릴지 모순 표시만 할지(제안: 모순 표시만), 하위 삭제·이동 같은 구조 변경으로 하위 전부 완료가 될 때 자동 완료할지(제안: 실행 상태 변경과 같게 처리), 상위가 Jira 상태 원본일 때의 상호작용(§13-7 연계), 상속된 선행 조건(F-H04)과 상위·하위 모순(F-H06)의 응답 표현. 상위 자동 완료 자체(F-H05)와 응답 필드의 골격은 ADR-0003 1.7과 ADR-0006 §8에 먼저 적었다. 초기 핵심 API 필드 모양이 여기서 굳는다 | §6.4, §6.9 F-H04~F-H06, §13-8, §13-16, AC-23, AC-25, AC-26, AC-28 |
| 그래프 배치·좌표 저장 | 좌표를 업무 데이터와 분리해 저장하고 `graph_revision`·`version` 대상에서 뺄지, 저장하지 않고 매번 자동 배치할지 정한다. CLI나 템플릿 적용으로 생겨 좌표가 없는 공정의 배치 규칙을 포함한다. 공정 계층이 생기면서 중첩(접기·펼치기) 배치와 층별 좌표 저장도 여기서 정한다. 선행관계가 형제끼리만이므로 자동 배치는 층마다 따로 돌릴 수 있다(OSS §4) | §13-4, F-G05, F-H07, §7.2 |
| 상세 설명 형식 | 원문을 텍스트로 저장한다는 합의만 먼저 하고 렌더링(Markdown 하위 집합 또는 평문)은 이월할 수 있다. 서버 최대 길이 검증과 Jira 게시 시 형식 변환을 함께 정한다 | §13-4, F-P04, §6.7 |

## 9. 스파이크 시나리오

OSS §12의 A·B·C·D 예제를 그대로 쓴다. 공정 A·B·C·D를 만들고 A → C, B → C를 연결한다. D는 독립 공정이다. A 완료, B 진행 중, C 미착수 상태를 쓴다.

공정 계층(PRD §6.9)을 확인하기 위해 상위 공정 '개발'과 그 하위 X·Y를 더한다. A → 개발, 개발 → B를 연결한다. 개발은 A·B·C·D와 같은 최상위 층이고, X·Y는 개발 안의 층이다. AC-25의 X·Y·Z를 X·Y로 줄인 것이다.

| 단계 | 확인할 결과 | 검증 기준 |
| --- | --- | --- |
| GUI에서 A·B·C·D 생성, A → C, B → C 연결 | 네 공정이 모두 보이고 연결 방향이 정확함 | AC-01 |
| 상태를 A 완료, B 진행 중, C 미착수로 설정 | 각 상태와 C의 미완료 선행 공정 B를 한 화면에서 확인 | AC-02 |
| C를 진행 중으로 변경 | 변경이 허용되고 B 미완료 정보가 유지됨 | AC-03 |
| C → A 추가를 GUI와 CLI에서 시도 | 서버가 순환으로 거부하고 기존 데이터 유지. 오류에 순환 경로 포함 | AC-04 |
| CLI로 공정·관계·상태를 바꾼 뒤 GUI 새로고침, 반대 방향도 확인 | 양쪽에서 같은 ID와 데이터가 보임 | AC-13 |
| 외부 인터넷을 차단하고 서버·웹·CLI 실행 | 기본 기능이 동작하고 외부 자산 요청이 없음 | AC-14 |
| 서로 연결이 없는 A와 B에 A → B와 B → A를 동시에 요청 | 저장된 그래프에 순환이 없고 거부된 요청은 이유를 받음 | AC-18 |
| GUI에서 상위 '개발'을 만들고 CLI로 `--parent`를 지정해 하위 X·Y 생성 | GUI에서 개발 아래에 X·Y가 같은 ID로 표시되고, 접힌 개발에 0/2가 표시됨 | AC-31 |
| A → 개발, 개발 → B를 연결하고 X·B의 선행 조건 조회 | X·Y의 선행 조건에 A가 상속된 선행(`inheritedFrom`: 개발)으로 포함되고, B의 선행 조건은 개발의 완료임 | AC-28 |
| X → B(다른 층) 추가를 GUI와 CLI에서 시도 | `CROSS_LEVEL_DEPENDENCY`로 거부되고 이유가 표시됨. 기존 데이터 유지 | AC-27 |
| 개발의 상위를 X로 지정 시도 | `HIERARCHY_CYCLE`로 거부되고 기존 구조 유지 | AC-29 |
| X 완료, 이어서 Y 완료 | X 완료 시 개발은 미완료에 1/2. Y 완료 시 개발이 같은 요청 안에서 자동 완료되고 응답에 자동 변경된 상위가 포함됨 | AC-25 |

이 시나리오로 ADR-0001(React Flow + Dagre + 서버 검증, 하위 흐름 표시), ADR-0003(프로젝트 단위 직렬화, 계층 검사와 상위 자동 완료), ADR-0006(변경 묶음과 오류 형식, 계층 오류 코드와 응답 필드), ADR-0007(종료 코드, `--parent`)의 핵심 가정을 함께 확인한다. 스파이크 결과는 해당 ADR의 '채택 전 확인할 사항'에 적는다. 채택한 ADR-0001·ADR-0002는 '남은 확인 사항'에 적는다.
