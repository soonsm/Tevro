## 배경

지금 Tevro는 공정에 Jira 이슈 주소를 적어 둘 수만 있다. 바라는 것은 Jira에 들어가지 않고 Tevro에서 Jira 일을 끝내는 것이다(roadmap §3).

1. Tevro 공정으로 Jira 이슈를 만든다.
2. Tevro에서 바꾼 상태가 Jira에 반영된다.
3. Jira에서 바뀐 상태가 Tevro에 보인다. 팀원은 Jira 보드에서도 카드를 옮긴다.

처음 확인한 환경(특정 사이트 값은 적지 않는다):

| 항목 | 확인한 내용 |
| --- | --- |
| 제품 | 설치형 Jira Data Center 9.x. REST API v2, Agile API v1 |
| 인증 | 개인 액세스 토큰(Bearer). 공용 서비스 계정은 쓸 수 없고 사람마다 자기 토큰을 쓴다 |
| 보드 | 칸반. 스프린트가 없다 |
| 필수 필드 | summary, issuetype, project, reporter, 그리고 사이트가 더한 사용자 정의 숫자 필드(기본값 0) |
| 선택 필드 | duedate(날짜), assignee(사용자) |
| 상태 | 다섯 개. 상태 분류(statusCategory)는 할 일 1개, 진행 중 2개, 완료 2개(하나는 '안 함' 성격). 전환할 때 강제 입력 필드 없음 |
| 이슈 유형 | 여러 개. 그중 하위 작업 유형만 상위 이슈가 필요하다 |
| 링크 유형 | blocks / is blocked by 있음 |
| 사용자 식별 | name, key, emailAddress, displayName |
| 네트워크 | Tevro 서버에서 Jira로 접속 가능, 외부 도구의 API 이슈 생성 허용 |

## 결정

### 1. 연결과 인증

- **Jira 사이트는 서버마다 하나.** 관리자가 `TEVRO_JIRA_URL`로 정한다. 정하지 않으면 지금처럼 이슈 주소만 적는 기능으로 남는다(PRD 원칙 4: Jira는 선택 연동).
- **사람마다 자기 토큰.** 각자 계정 메뉴의 **Jira 연결**에서 Jira 개인 액세스 토큰을 등록한다. 등록할 때 `/rest/api/2/myself`로 확인하고 Jira `name`·`displayName`을 함께 저장한다. Tevro가 Jira를 부를 때는 **그 작업을 누른 사람의 토큰**만 쓴다. 그래서 Jira 권한을 우회해 이슈를 만들거나 옮길 수 없다.
- **토큰 저장.** 서버 비밀키 `TEVRO_SECRET_KEY`(32바이트)로 AES-256-GCM 암호화해 저장한다. 키가 없으면 토큰 등록을 막고 이유를 알린다. 설치 스크립트와 Docker 안내가 키를 만든다. 키를 잃으면 모두 토큰을 다시 등록해야 한다. 응답과 로그에는 토큰을 넣지 않는다.
- **CLI·에이전트.** 에이전트는 Tevro 토큰으로 Tevro를 부르고, Tevro는 그 Tevro 사용자의 Jira 토큰으로 Jira를 부른다. 에이전트가 Jira 토큰을 따로 갖지 않는다.

### 2. 프로젝트 연결 설정

Tevro 프로젝트마다 편집자 이상이 한 번 정한다.

| 설정 | 내용 |
| --- | --- |
| Jira 프로젝트 | 키 하나 |
| 기본 이슈 유형 | 만들기 창에 미리 골라 두는 값일 뿐이다. 이슈마다 만들 때 바꾼다(아래 §3). 하위 작업 유형은 고를 수 없다(상위 이슈가 필요해서. 후속 검토) |
| 상태 짝(Tevro → Jira) | 미착수·진행 중·완료 각각을 Jira 상태 하나에 짝짓는다. Tevro가 상태 분류로 추천값을 채운다. 같은 분류에 상태가 여럿이면 워크플로 순서상 앞의 것(예: '완료'와 '안 함' 중 '완료')을 추천하고 사람이 확인한다 |
| 선후관계 링크 유형 | 'A가 B를 막는다'를 뜻하는 링크 유형과 방향. blocks 계열이 있으면 추천한다 |

### 3. 이슈 만들기(F-J05~F-J09)

- **대상은 사람이 고른다.** 공정 패널의 [Jira 이슈 만들기]와, 여러 공정을 고르는 일괄 만들기. 일괄 만들기의 기본 선택은 아직 연결되지 않은 **말단 공정**이다(상위 공정까지 이슈가 되면 Jira가 지저분해진다). 상위 공정도 직접 고르면 만들 수 있다.
- **이슈 유형은 만들 때 정한다.** 만들기 창에서 그 Jira 프로젝트의 이슈 유형 목록(하위 작업 유형 제외)을 보이고, 프로젝트 설정의 기본 유형을 미리 골라 둔다. 일괄 만들기는 공정마다 유형을 따로 고를 수 있고, '모두 같은 유형으로' 한 번에 바꾸는 칸도 둔다. 유형마다 필수 필드가 다를 수 있으므로 필수 필드는 고른 유형 기준으로 다시 읽는다.
- **넘기는 값.** 제목 → summary, 설명 → description(평문), 기한 → duedate, 담당자 → assignee(그 사람의 Jira name을 알 때), 만드는 사람 → reporter.
- **사이트별 필수 필드는 실행할 때 묻는다.** 만들기 전에 createmeta로 필수 필드를 읽고, Tevro가 채우지 못하는 필드(예: 스토리 포인트)는 만들기 창에 칸으로 띄운다. 숫자·문자·날짜·정해진 값 고르기를 지원한다. 일괄 만들기는 공정마다 한 줄씩 받고, 기본값(사이트 기본값, 없으면 그 프로젝트에서 마지막에 쓴 값)을 채워 둔다. 특정 필드 번호를 코드에 넣지 않는다. 지원하지 않는 형식의 필수 필드가 있으면 만들기를 막고 이유를 보인다.
- **미리 보기(F-J07).** 대상 프로젝트, 이슈 유형, 필수 필드, 만들 공정, 이미 연결돼 건너뛸 공정, 만들 링크를 실행 전에 보인다.
- **만든 뒤 상태 맞추기.** 이미 진행 중이거나 완료인 공정은, 이슈를 만든 직후 짝 표대로 Jira 상태를 옮긴다. 그래서 새로고침했을 때 미착수로 되돌아가는 문제(PRD '상태 원본 전환')가 생기지 않는다.
- **선후관계 링크(F-J08).** 만들기 창의 체크(기본 켬). 양쪽 공정이 모두 Jira에 연결돼 있을 때만, 방향을 지켜 만든다. 같은 이슈를 가리키는 두 공정 사이는 건너뛴다. 이미 같은 방향 링크가 있으면 다시 만들지 않는다. 나중에 [선후관계를 Jira에 반영]으로 다시 할 수 있다.
- **부분 성공과 재시도.** 공정·링크마다 결과(성공, 실패와 이유, 결과 미확인)를 저장하고 보인다. 성공한 것은 다시 하지 않는다. 응답을 받지 못한 생성은 '결과 미확인'으로 두고, 재시도 전에 JQL(같은 프로젝트·같은 제목·본인이 보고자·최근 생성)로 찾아 있으면 연결한다. 전체를 하나의 원자적 작업으로 보지 않는다.
- **동시 실행.** 일괄 작업은 Jira에 동시에 4개까지만 요청하고, 429·503이면 `Retry-After`를 따른다.

### 4. 상태·기한·담당자(F-J10~F-J14, 상태 원본)

- **연결된 공정의 실행 상태·기한·담당자는 Jira가 원본이다.** 팀원이 Jira 보드에서도 카드를 옮기고 기한·담당자를 바꾸기 때문이다. 상태만 따라가고 기한·담당자가 따로 놀면 지연 표시와 '내가 맡은 일'이 틀어진다.
- **Jira → Tevro.** 상태 분류로 바꾼다: 할 일 → 미착수, 진행 중 → 진행 중, 완료 → 완료. 카드와 패널에 Jira 상태 이름도 함께 보인다. 그래서 '완료' 분류의 '안 함' 같은 상태는 Tevro에서 완료(선행 조건을 풀어 줌)로 치되 이름으로 구분된다. 분류를 알 수 없는 상태는 '확인 필요'로 표시한다(F-J12).
- **Jira → Tevro 기한·담당자.** duedate → 기한. assignee는 짝지은 Tevro 사용자가 있으면 그 사람을 담당자로, 없으면 Tevro 담당자는 비우고 Jira 표시 이름만 카드에 보인다('내가 맡은 일'에는 넣지 않음).
- **Tevro → Jira.** 연결된 공정의 상태·기한·담당자를 Tevro(화면·CLI)에서 바꾸면, 누른 사람의 토큰으로 Jira에 먼저 반영한 뒤에 Tevro에 저장한다. 상태는 짝 표의 상태로 전환하고, 바로 가는 전환이 없으면 워크플로의 전환을 따라 최대 3단계까지 찾아 거친다. Jira 사용자와 짝짓지 않은 Tevro 사용자는 담당자로 넘길 수 없다. 실패하면 Tevro 값도 바꾸지 않고 이유를 보인다. Jira 토큰이 없는 사람은 연결된 공정의 이 세 값을 바꿀 수 없다.
- **덮어쓰기 확인.** 바꾸기 직전에 그 이슈를 다시 읽는다. 마지막 조회 뒤 Jira에서 그 값이 바뀌었으면 바꾸지 않고 'Jira에서 ○○로 바뀌었습니다'를 알린다(409 `JIRA_CHANGED`, 최신 값 포함). 화면은 확인을 받은 뒤 다시 보낸다.
- **가져오는 때.** 아래 경우에, 요청한 사람의 토큰으로 JQL(`key in (...)`, 100개씩)로 가져온다.
  - 프로젝트를 읽는 모든 요청(웹·API·CLI·에이전트): 마지막 조회 뒤 5분이 지났으면 먼저 가져온 뒤 답한다. 요청한 사람에게 Jira 토큰이 없거나 조회에 실패하면 저장된 값으로 답하고 마지막 조회 시각을 함께 준다. 조회 실패가 읽기를 막지 않는다.
  - 웹 화면을 열어 두는 동안: 탭이 보이면 5분마다 다시 읽는다(위 규칙에 따라 필요할 때만 Jira를 부른다).
  - [Jira에서 새로고침]·`tevro jira refresh`: 5분과 상관없이 바로.
  - 이슈를 만들거나 연결한 직후, 바꾸기 직전(그 이슈 하나).
- **주기 조회·웹훅은 하지 않는다.** 서버가 혼자 조회하려면 누군가의 개인 토큰을 그 사람이 모르게 써야 한다. 즉시 반영이 필요하면 Jira 관리자에게 웹훅 등록을 요청하는 후속 작업으로 둔다. 그래서 반영은 사람이 볼 때 기준으로 최대 5분 늦다.
- **조회 결과는 모두에게 공유한다.** 마지막으로 조회한 이슈 상태·제목·기한·담당자는 Tevro에 저장해 프로젝트를 볼 수 있는 모두에게 보인다. Jira 권한이 없는 Tevro 사용자도 그 값은 보게 된다. 같은 팀이 쓰는 도구라 받아들이고, 화면에 '마지막 조회 시각과 조회한 사람'을 보인다(F-J13). 조회에 실패한 이슈는 이전 값을 지우지 않고 실패로 표시한다(F-J14).
- **상위 공정.** 상위 공정이 Jira에 연결돼 있으면 그 상태도 Jira를 따르며, 하위가 모두 완료돼도 자동 완료하지 않고 모순으로 표시한다(PRD F-H05).

### 5. 연결과 해제(F-J02, F-J04)

- **기존 이슈 연결.** 지금의 'Jira 이슈 주소' 칸이 연결이 된다. 연결하면 첫 조회 때 Jira 상태가 Tevro 상태를 덮는다. 연결 전에 Tevro 상태와 Jira 상태가 다르면 무엇으로 바뀌는지 먼저 보이고 확인을 받는다. 연결 전 상태는 따로 보관하지 않는다.
- **해제.** Tevro의 연결만 지운다. Jira 이슈·링크는 지우지 않는다. 해제 뒤 상태는 마지막으로 조회한 값으로 두고, 이후 Tevro에서 직접 바꾼다.
- **사이트 밖 주소.** `TEVRO_JIRA_URL`과 다른 사이트의 주소는 지금처럼 링크로만 둔다(상태 연동 없음).

### 6. 만든 뒤 바뀌는 다른 값

제목·설명은 만들 때 한 번 넘긴다(Jira 설명은 위키 서식이라 오가며 깨질 수 있고, 공정 이름과 이슈 제목이 달라도 되는 경우가 많다). 이후 양쪽에서 바꿔도 서로 따라가지 않는다(PRD '정보의 원본 원칙'). 화면에 'Jira에는 반영되지 않습니다'를 보인다. 선후관계를 Tevro에서 지워도 Jira 링크는 지우지 않는다. 반영한 링크와 지금 관계가 다르면 차이를 표시한다.

### 7. 하지 않는 것

스프린트(칸반에는 없다. 스크럼 보드를 쓰는 팀이 생기면 검토), 웹훅·주기 조회, 제목·설명과 그 밖의 필드의 양방향 동기화, 하위 작업 유형, Jira Cloud(인증 방식이 달라 후속 검토), 여러 Jira 사이트.

| `users` 추가 칸 | (관리자가 짝지은) Jira name. 토큰을 등록한 사람은 토큰 등록 때 채운다 |

## API·CLI(요지)

- API: `PUT /api/v1/me/jira-token`, `GET/PUT /api/v1/projects/:id/jira`, `POST /api/v1/projects/:id/jira/preview`, `POST /api/v1/projects/:id/jira/issues`, `POST /api/v1/projects/:id/jira/refresh`, `POST /api/v1/projects/:id/jira/links`. 상태 변경은 지금의 `PATCH /tasks/:id`가 연결된 공정이면 Jira 전환을 거친다.
- 새 오류 코드: `JIRA_CHANGED`(마지막 조회 뒤 Jira에서 바뀜), `JIRA_NOT_CONFIGURED`, `JIRA_TOKEN_REQUIRED`, `JIRA_AUTH`(토큰 만료·권한), `JIRA_UNAVAILABLE`(접속·시간 초과), `JIRA_REJECTED`(Jira가 거부, 사유 포함), `JIRA_TRANSITION`(갈 수 있는 전환 없음).
- CLI: `tevro jira token set --stdin`, `tevro jira setup`, `tevro jira create [--task ...] [--field 이름=값] [--dry-run]`, `tevro jira refresh`, `tevro jira links`. 부분 성공은 별도 종료 코드로 알린다(ADR-0007의 미결 항목).

## 검토한 선택지

| 선택지 | 판단 |
| --- | --- |
| 공용 서비스 계정 하나 | 쓸 수 없다(확인한 환경). 권한 우회 문제도 있다(PRD §6.7) |
| Tevro가 상태 원본, Jira에는 보내기만 | 팀원이 Jira 보드에서 카드를 옮기면 두 곳이 어긋난다. 채택하지 않음 |
| 사이트 고유 필수 필드를 Tevro 공정 칸으로 추가 | 특정 사이트 설정에 Tevro가 묶인다. 실행할 때 묻는 방식 채택 |
| 상태 짝 없이 분류만으로 자동 전환 | 같은 분류에 '완료'와 '안 함'이 함께 있어 틀린 상태로 옮길 수 있다. 짝 표 채택 |
| 웹훅으로 즉시 반영 | Jira 관리자 등록과 Tevro로 들어오는 경로가 필요하다. 후속 |

## 남은 확인 사항

- 설명 필드 렌더러(위키 스타일이면 평문 일부가 서식으로 해석될 수 있다)
- 일괄 생성 때 Jira 쪽 호출 제한 값
- 사용자 짝짓기: Tevro 아이디와 Jira name이 같은 조직이면 자동 짝짓기 옵션을 둘지

## 구현 순서

1. 토큰 등록·암호화, 프로젝트 연결 설정, 기존 이슈 연결과 상태 가져오기(F-J01~F-J04, F-J10~F-J14)
2. Tevro에서 상태 바꾸면 Jira 전환
3. 이슈 만들기(하나·일괄, 필수 필드 묻기, 미리 보기, 결과 저장)와 선후관계 링크
4. CLI
