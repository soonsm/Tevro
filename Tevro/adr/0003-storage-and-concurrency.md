## 배경

PRD §7.2는 다음 세 가지를 요구한다.

- 삭제되는 공정을 참조하는 연결이 남지 않도록 일관성을 유지한다.
- 오래된 화면이나 에이전트가 다른 사용자의 변경을 무조건 덮어쓰지 않도록 충돌을 식별한다.
- 동시에 들어온 여러 구조 변경도 최종 저장 결과가 DAG 규칙을 만족해야 한다.

이 ADR 작성 당시(2026-10-07) §13-2는 저장 방식, 백업·복구, 동시 수정 충돌 처리를 구현 전 결정 사항으로 두었다. 현재 §13-2는 이 ADR의 결정을 반영했다. F-C05는 동시 수정 충돌을 구분하는 종료 코드를, N-04는 백업·복구를 요구한다. 스키마와 트랜잭션 경계, 충돌 오류가 정해지지 않으면 공정·종속성 API([ADR-0006](./0006-server-api-contract.md))와 CLI 종료 코드([ADR-0007](./0007-cli-contract.md))를 확정할 수 없다.

저장소 선택은 배포 형태에 묶인다. [ADR-0002](./0002-deployment-packaging.md)는 2026-10-08 선택지 B(Node.js 런타임 동봉 tar.gz + systemd 단일 프로세스)로 채택됐다. 같은 결정에서 사내 PostgreSQL(사내 DB 서비스 또는 플랫폼 안 운영)은 쓸 수 없다고 확인됐다.

핵심 함정은 순환 금지가 프로젝트 전체에 걸린 불변식이라는 점이다. 행 단위 잠금이나 유니크 제약만으로는 막을 수 없다. 공정 A, B가 있고 연결이 없는 프로젝트(graph_revision = 7)에서 사용자가 A → B를, 에이전트가 동시에 B → A를 추가하는 경우를 보자.

행 단위 검증만 할 때:

| 시점 | 요청 1(사용자, A → B) | 요청 2(에이전트, B → A) |
| --- | --- | --- |
| t1 | 현재 연결을 읽음: 없음 | 현재 연결을 읽음: 없음 |
| t2 | 순환 없음으로 판정 | 순환 없음으로 판정 |
| t3 | (A, B) 행 삽입. 유니크 제약 통과 | (B, A) 행 삽입. 다른 행이므로 유니크 제약 통과 |
| t4 | 커밋 | 커밋. A → B와 B → A가 함께 저장되어 순환이 생김 |

결과는 F-D04, F-D06, AC-18 위반이다.

프로젝트 단위로 구조 변경을 직렬화할 때:

| 시점 | 요청 1(사용자, A → B) | 요청 2(에이전트, B → A) |
| --- | --- | --- |
| t1 | 프로젝트 잠금 획득 | 같은 프로젝트 잠금을 기다림 |
| t2 | 연결 없음 → A → B 검증 통과 → 삽입 → graph_revision 8 → 커밋, 잠금 해제 | 대기 |
| t3 | — | 잠금 획득 → 연결 A → B를 읽음 → B → A는 순환 → `VALIDATION_CYCLE`(경로 B → A → B)로 거부 |

저장된 그래프에 순환이 없고, 거부된 요청은 이유를 받는다. AC-18을 만족한다.

PRD §6.9 공정 계층은 두 번째 관계를 더한다. 공정은 상위 공정을 최대 하나 가질 수 있고(포함관계, `parent_id`), 포함관계는 트리여야 하며, 선행관계는 같은 상위 안의 형제끼리만 맺는다(R1~R3). 자기 자신이나 자손을 상위로 지정하는 변경을 막으려면 조상 경로를 따라 올라가야 한다. 이것도 순환 금지와 같은 종류의 프로젝트 전체 불변식이라 행 단위 제약으로는 막을 수 없다. 두 요청이 동시에 '개발의 상위를 X로', 'X의 상위를 개발로' 바꾸면 각각은 유효해 보여도 합치면 트리가 깨진다. 그래서 계층 검사도 아래 1.1의 직렬화 안에 둔다. 하위가 모두 완료되면 상위를 자동으로 완료로 바꾸는 규칙(F-H05)을 어느 트랜잭션에서 적용할지도 정해야 한다.

## 결정

2026-10-08 결정권자가 저장소로 선택지 B(SQLite)를, Node.js 드라이버로 `better-sqlite3`를 채택했다. 동시 수정 모델(1)은 제안대로 채택했다.

| 항목 | 결정 |
| --- | --- |
| 저장소 | SQLite. WAL 모드, 서버 인스턴스 하나, 같은 호스트의 로컬 디스크(2, 선택지 B) |
| Node.js 드라이버 | `better-sqlite3`(2) |
| 동시 수정 모델 | 제안대로 채택. 모든 쓰기 트랜잭션을 `BEGIN IMMEDIATE`로 여는 단일 writer, 프로젝트 `graph_revision`, 공정 `version`, DB 제약, 좌표·Jira 조회 결과의 분리 테이블(1.1~1.6) |
| 기대 버전 생략 | 허용(제안과 같음). GUI는 항상 보낸다. CLI·스크립트가 생략하면 지정한 필드만 바꾸는 부분 수정으로 처리한다. AC-17은 기대 버전을 보낸 요청에 대해 보장된다(1.3) |
| 상위가 있는 공정의 실행 상태 변경 | 프로젝트 잠금 안에서 처리한다(제안과 같음). `graph_revision`은 올리지 않는다(1.7) |

결정권자가 명시적으로 답한 범위는 저장소(SQLite), 드라이버(`better-sqlite3`), 기대 버전 생략 허용(1.3), 상위가 있는 공정의 실행 상태 변경 잠금(1.7)이다. 결정권자는 동시 수정 모델 자체(1.1~1.6)에 대해 별도 수정 요청을 하지 않았다. 그래서 이 모델은 제안 그대로 채택한 것으로 기록한다. 백업·복구(3)에는 따로 답하지 않았다. 3의 방식은 SQLite 결정에 맞춘 작성자 제안으로 둔다. 업데이트 전 백업은 [ADR-0002](./0002-deployment-packaging.md) '업데이트·롤백' 원칙으로 채택됐다.

제안과 달라진 점: 드라이버는 결정 과정에서 내장 `node:sqlite`를 먼저 제안했으나 결정권자가 `better-sqlite3`를 선택했다. 선택 사유는 기록되지 않았다. 제안 단계 원문은 2의 '채택하지 않은 안' 행에 그대로 둔다.

결정 과정에서 PostgreSQL을 직접 운영하는 안도 검토했으나 SQLite로 정했다. 사유는 기록되지 않았다.

이번 결정에서 정하지 않은 것은 다음과 같다.

- 계층 자동 전이의 세부 (a)(b)(c)(1.7 '상위 자동 완료'). 결정 필요로 남고 PRD §13-16에서 정한다.
- 예상 규모(동시 사용자, 프로젝트당 공정 수, 계층 깊이)와 백업 보관 기준. '남은 확인 사항'에 둔다.

### 1. 동시 수정 모델 — 제안대로 채택

제안 단계에서는 저장소 선택과 무관한 모델로 제안했다. 아래는 채택한 SQLite 기준으로 정리했다.

**1.1 graph_revision: 구조 변경의 직렬화**

- 프로젝트마다 정수 `graph_revision`을 둔다.
- '구조 변경'은 공정 생성·삭제, 공정의 상위 지정·변경(변경 묶음 작업 `task.move`, 1.7), 종속성 추가·삭제, 그리고 이를 포함한 변경 묶음(change set, ADR-0006)이다.
- 구조 변경은 한 트랜잭션 안에서 다음 순서로 처리한다.
  1. 프로젝트 잠금을 얻는다. 모든 쓰기 트랜잭션은 `better-sqlite3`의 `db.transaction()`이 돌려주는 트랜잭션 함수의 `immediate` 변형으로 연다. 이 변형은 `BEGIN IMMEDIATE`를 쓴다 [better-sqlite3 API][bs3-api]. SQLite는 쓰기 트랜잭션을 한 번에 하나만 처리하므로(단일 writer) 프로젝트 잠금이 자연히 충족된다.
  2. 그 프로젝트의 현재 공정·종속성을 읽는다.
  3. 변경을 적용한 최종 상태를 한 번 검증한다. 계층부터 검사하고(자기 자신·자손을 상위로 지정, 다른 프로젝트의 상위, 연결이 남은 공정의 상위 변경, 1.7), 그다음 선행관계를 검사한다(자기 참조, 중복, 존재하지 않는 참조, 다른 프로젝트 참조, 다른 층 사이 연결, 층별 순환).
  4. 쓴다.
  5. `graph_revision`을 1 올린다.
  6. 커밋한다.
- 제안 단계에서 함께 적었던 PostgreSQL 방식(프로젝트 행 `SELECT … FOR UPDATE`)은 채택하지 않았다(선택지 A).
- 클라이언트가 기대 리비전(`expectedGraphRevision`)을 보냈는데 현재 값과 다르면 `CONFLICT`로 거부한다. 보내지 않으면 현재 그래프 기준으로 검증만 한다. 검증은 항상 잠금 안에서 하므로 기대 리비전이 없어도 DAG 불변식은 지켜진다.
- 공정 생성도 구조 변경에 넣는다. dry-run과 실제 실행을 묶을 때(ADR-0006) 그 사이에 추가된 공정도 감지해야 하기 때문이다.
- 상위 변경(`task.move`)도 구조 변경이다. 형제가 바뀌면 어느 선행관계가 유효한지가 바뀌고, 검증이 층 단위로 이루어지기 때문이다(1.7).

**1.2 version: 공정 필드의 낙관적 잠금**

- 공정마다 정수 `version`을 둔다.
- 필드 수정(제목, 설명, 실행 상태, 선택 정보)은 `UPDATE … SET …, version = version + 1 WHERE id = ? AND version = ?`로 처리한다. 필드 수정도 쓰기 트랜잭션이므로 1.1과 같이 `immediate` 변형으로 연다.
- 영향받은 행이 0이면, 공정이 있으면 `CONFLICT`, 없으면 `NOT_FOUND`다. 변경 묶음 안의 `task.update`도 같다([ADR-0005](./0005-identifiers-and-deletion.md) '삭제된 ID의 오류').
- HTTP는 `If-Match`(ETag = version), 변경 묶음은 작업별 `expectedVersion`, CLI는 `--expected-version`으로 기대 버전을 전달한다.
- 필드 수정은 `graph_revision`을 올리지 않는다. 그래서 제목 편집과 종속성 추가가 서로 충돌로 처리되지 않는다.

**1.3 기대 버전 생략 — 결정: 허용**

2026-10-08 결정권자가 제안대로 생략 허용을 채택했다.

| 방식 | 내용 | 영향 |
| --- | --- | --- |
| 생략 허용 — 채택 | GUI는 항상 보낸다. CLI·스크립트는 생략할 수 있고, 생략하면 지정한 필드만 바꾸는 부분 수정으로 처리한다. 응답에 새 version을 돌려준다 | 비대화형 스크립트(F-C03)가 쓰기 쉽다. AC-17은 기대 버전을 보낸 요청에 대해 보장된다 |
| 항상 필수 — 채택하지 않음 | 기대 버전이 없는 수정은 입력 오류로 거부한다 | §7.2를 가장 엄격하게 만족한다. 스크립트는 매번 조회 후 수정해야 한다 |

**1.4 DB 제약으로 한 번 더 막기**

| 제약 | 막는 것 |
| --- | --- |
| 종속성 `UNIQUE(project_id, from_task_id, to_task_id)` | 중복 연결(F-D04, AC-16) |
| 종속성 `CHECK(from_task_id <> to_task_id)` | 자기 참조(F-D04, AC-16) |
| 공정 `UNIQUE(project_id, id)`와 종속성의 `(project_id, from_task_id)`·`(project_id, to_task_id)` 복합 외래 키 | 다른 프로젝트 공정 참조(PRD §6.2 하단, OSS §5.2) |
| 종속성 외래 키 `ON DELETE CASCADE` | 삭제된 공정을 참조하는 연결(§7.2, F-P06) |
| 공정 `(project_id, parent_id)` → 공정 `(project_id, id)` 복합 외래 키. `parent_id`는 NULL 허용 | 다른 프로젝트의 공정을 상위로 지정(F-H02). NULL이면 최상위 공정이다 |
| 공정 `CHECK(parent_id IS NULL OR parent_id <> id)` | 자기 자신을 상위로 지정(F-H02) |

순환은 DB 제약으로 표현할 수 없다. 자손을 상위로 지정해 트리를 깨는 변경도 같다(1.7). 1.1의 잠금 안 검증이 유일한 방어선이다. SQLite는 외래 키 제약이 기본 비활성이며 연결마다 `PRAGMA foreign_keys = ON`으로 켜야 한다. [SQLite 외래 키][sqlite-fk]

**1.5 구조 리비전·버전에서 분리할 데이터**

- 노드 좌표와 Jira 조회 결과(상태 조회 정보, 반영 결과)는 별도 테이블에 두고 `graph_revision`과 `version`을 올리지 않는다.
- 노드를 옮기거나 Jira 상태를 새로고침한 것만으로 다른 사용자의 편집이 충돌로 처리되지 않게 하기 위해서다.
- 좌표 저장 여부와 범위는 후속 ADR 후보 '그래프 배치·좌표 저장'에서 정한다([README](./README.md)).

**1.6 접근 경로**

DB에는 서버만 접근한다. CLI와 웹은 서버 API만 쓴다(F-C08, OSS §8.2).

**1.7 공정 계층: 트리 제약, 상위 변경, 상위 자동 완료**

PRD §6.9의 규칙을 저장소와 트랜잭션으로 옮기면 다음과 같다.

| 항목 | 내용 |
| --- | --- |
| 스키마 | 공정 테이블에 `parent_id`(NULL 허용)를 둔다. 1.4의 복합 외래 키로 같은 프로젝트의 공정만 가리키게 하고, CHECK로 자기 참조를 막는다. 종속성 테이블은 바꾸지 않는다. 포함관계를 종속성 행에 섞지 않는다 |
| 트리·자손 검사 | 자손을 상위로 지정하는 변경은 DB 제약으로 표현하기 어렵다. 서버가 1.1의 잠금 안에서 새 상위부터 최상위까지 조상 경로를 따라 올라가고, 경로에 변경 대상 공정이 나오면 `HIERARCHY_CYCLE`로 거부한다(F-H02, AC-29). 포함관계는 트리라 이 검사만 통과하면 순환이 생기지 않는다. 깊이 제한은 모델에 두지 않는다 |
| 층 단위 선행관계 | 종속성의 선행·후속 공정은 `parent_id`가 같아야 한다(둘 다 NULL인 최상위 포함). 다르면 `CROSS_LEVEL_DEPENDENCY`로 거부한다(F-H03, AC-27). 각 층은 독립된 DAG이므로 순환 검사는 층마다 따로 한다. 프로젝트 전체를 한 그래프로 검사해도 결과는 같지만, 층별 검사가 순환 경로를 작게 만든다 |
| 상위 변경(`task.move`) | 구조 변경으로 분류해 1.1의 직렬화를 타고 `graph_revision`을 올린다. 대상 공정에 선행·후속 연결이 하나라도 남아 있으면 `HAS_DEPENDENCIES`로 거부한다(F-H08, AC-32). 같은 변경 묶음 안에서 `dependency.remove`를 먼저 담으면 최종 상태에 연결이 없으므로 통과한다(ADR-0006). 하위 공정은 대상과 함께 움직이고, 하위 사이의 연결은 형제 관계가 유지되므로 그대로 둔다 |
| 상위 자동 완료(F-H05) | 실행 상태 변경으로 어떤 상위의 직접 하위가 모두 완료되면, 같은 트랜잭션 안에서 그 상위를 완료로 바꾸고(`version` + 1) 다시 그 상위의 형제를 보며 체인을 따라 올라간다. 상위가 Jira 상태 원본이면 거기서 멈추고 자동 변경 대신 모순으로 표시한다. 자동으로 바뀐 상위 목록을 응답에 담는다(ADR-0006 §8). 하위 착수 시 상위를 진행 중으로 바꿀지(a, 제안: 예), 자동 완료 후 하위를 다시 열었을 때 상위를 되돌릴지(b, 제안: 모순 표시만), 하위 삭제(`task.delete`)·이동(`task.move`) 같은 구조 변경으로 하위 전부 완료가 될 때도 같은 규칙을 적용할지(c, 제안: 실행 상태 변경과 같게 처리)는 결정 필요이며 PRD §13-16에서 정한다. 2026-10-08 결정에서도 정하지 않았다 |
| 자동 완료의 잠금 | 실행 상태 변경은 필드 수정이라 `graph_revision`을 올리지 않는다(1.2). 그러나 하위 X·Y의 완료가 동시에 들어오면 각 요청이 상대를 미완료로 읽어 상위 자동 완료를 둘 다 놓칠 수 있다. 결정(2026-10-08, 제안과 같음): 상위가 있는 공정의 실행 상태 변경은 1.1과 같은 프로젝트 잠금 안에서 처리한다. 형제 하위의 상태도 같은 트랜잭션 안에서 읽는다. `graph_revision`은 그대로 둔다. SQLite는 모든 쓰기를 `BEGIN IMMEDIATE`로 열므로 이 조건은 자연히 충족된다 |
| 수동 변경과 모순 | 상위의 실행 상태를 사용자가 직접 바꾸는 것은 막지 않는다(F-H06, AC-26). '상위 완료인데 하위 미완료', '하위 전부 완료인데 상위 미완료'는 저장하지 않고 조회 시 계산해 표시한다 |
| 저장하지 않는 것 | 상속된 선행 조건(F-H04), 직접 하위 수와 완료 수(`childCount`·`doneChildCount`), 상위·하위 모순은 저장하지 않고 조회 시 계산한다. 상태 요약(F-S05)도 말단 공정 기준으로 조회 시 계산한다(F-H09). 저장하면 상위 변경과 상태 변경마다 갱신해야 하고 불일치가 생길 수 있다. 조회는 어차피 프로젝트 그래프 전체를 읽는다(트레이드오프 참조) |
| 하위가 있는 공정의 삭제 | `parent_id` 외래 키의 삭제 동작은 ADR-0005의 결정을 따른다. 하위까지 삭제(제안)면 `ON DELETE CASCADE`, 한 단계 올림이면 서버가 같은 트랜잭션에서 하위의 `parent_id`를 먼저 바꾼다 |

### 2. 저장소 — SQLite(WAL, 단일 인스턴스), 드라이버 better-sqlite3

결정권자가 저장소를 SQLite로 정했다. SQLite 파일은 [ADR-0002](./0002-deployment-packaging.md) '컨테이너 대비'의 데이터 디렉터리에 둔다. 두 DB를 함께 지원하는 것은 목표로 두지 않고, 저장소 접근은 리포지토리 계층으로 감싸 교체 비용만 낮추는 것을 제안한다. 결정권자가 이 부분에 따로 답하지 않았으므로 작성자 제안으로 둔다.

제안 단계에서는 ADR-0002의 배포 형태 결과에 맞춰 고르는 것을 제안했다(기록).

| ADR-0002 결과 | 제안 저장소 | 결정 시점 판단(2026-10-08) |
| --- | --- | --- |
| 선택지 A(OCI·OpenShift) | 선택지 A: PostgreSQL | ADR-0002가 A를 채택하지 않았고 사내 PostgreSQL을 쓸 수 없어 해당 없음 |
| 선택지 B(tar.gz 단일 호스트) | 선택지 B: SQLite(WAL, 단일 인스턴스) | ADR-0002가 B를 채택했다. 결정권자가 SQLite를 채택했다 |

SQLite 구현 시 주의점은 다음과 같다.

| 항목 | 내용 |
| --- | --- |
| 쓰기 잠금 | 모든 쓰기 트랜잭션을 `better-sqlite3` 트랜잭션 함수의 `immediate` 변형(`BEGIN IMMEDIATE`)으로 연다 [better-sqlite3 API][bs3-api]. `BEGIN DEFERRED`로 읽은 뒤 쓰면 쓰기 전환에 실패해 `SQLITE_BUSY`가 날 수 있다. 대기 시간(busy timeout)을 설정한다 [SQLite 트랜잭션][sqlite-tx] |
| 동시성 범위 | 쓰기 트랜잭션은 한 번에 하나다. WAL에서 읽기는 쓰기를 막지 않는다(DB 수준). 모든 프로세스가 같은 호스트에 있어야 하고 네트워크 파일 시스템은 쓸 수 없다 [SQLite WAL][sqlite-wal]. 다만 `better-sqlite3`는 동기식이라 같은 프로세스·스레드 안에서는 읽기와 쓰기가 하나씩 실행된다(API 형태, 트레이드오프). 서버 인스턴스는 하나다. 쓰기 연결도 하나로 두는 것을 제안한다(3, 작성자 제안) |
| Node.js 드라이버 | `better-sqlite3`. 2026-10-08 확인한 최신 버전은 13.0.3이다. 확인한 사실이며 고정 버전은 아니다. 고정 버전은 ADR-0001 후속 작업(채택 패키지의 고정 버전 기록, OSS §11.1)에서 정한다. 라이선스 MIT. `engines`는 `node >=22`라 ADR-0001의 Node.js 26이 범위에 든다. 의존성은 `node-addon-api` `^8.0.0`이다 [better-sqlite3 npm 메타데이터][npm-better-sqlite3] |
| 미리 빌드된 바이너리 | `better-sqlite3`는 네이티브 애드온이다. npm 패키지에 install 스크립트가 없고, 패키지 안 `prebuilds/`에 미리 빌드된 `.node` 바이너리가 들어 있다(darwin-arm64, darwin-x64, linux-arm64, linux-x64, linuxmusl-arm64, linuxmusl-x64, win32-arm64, win32-x64 등. 2026-10-08 npm 배포물 직접 확인). 설치할 때 외부에서 내려받는 것이 없어 내부 npm 미러로 설치할 수 있다. README도 주요 플랫폼·아키텍처용 미리 빌드된 바이너리를 제공한다고 밝힌다 [better-sqlite3 README][bs3-readme]. 대상 서버의 OS·아키텍처가 이 목록에 있는지는 '남은 확인 사항'이다 |
| 번들 SQLite | 기본 배포는 SQLite 3.53.4를 번들한다 [better-sqlite3 compilation 문서][bs3-compilation] |
| API 형태 | 동기식 API다 [better-sqlite3 README][bs3-readme]. 쿼리가 실행되는 동안 Node.js 이벤트 루프가 막힌다. 프로젝트 그래프가 작다는 가정에 기대며, 규모 확인 대상이다(트레이드오프) |
| 종료 | 종료 신호(SIGTERM)를 받으면 새 요청을 거절하고, 진행 중인 요청과 트랜잭션을 마무리한 뒤 DB를 닫고 종료한다([ADR-0002](./0002-deployment-packaging.md) '컨테이너 대비', 2026-10-08 채택) |
| 채택하지 않은 안: 내장 `node:sqlite` | 제안 단계 원문(기록): '내장 `node:sqlite`(v22.5.0 추가, 현재 문서 기준 Stability 1.2 Release candidate) 또는 네이티브 애드온. 네이티브 애드온이면 플랫폼별 빌드물을 반입해야 한다' [node:sqlite][node-sqlite]. 2026-10-08에도 Node.js 26 문서 기준 Stability 1.2 Release candidate다. 결정 과정에서 `node:sqlite`를 먼저 제안했으나 결정권자가 `better-sqlite3`를 골랐다. 선택 사유는 기록되지 않았다 |

### 3. 백업·복구 — 첫 운영 설치 전 완성

착수를 막지는 않지만, 첫 운영 설치 전에 절차 문서와 복구 시험을 마치는 것을 제안한다(N-04, AC-24). 결정권자가 이 절에 따로 답하지 않았으므로 아래 방식은 SQLite 결정에 맞춘 작성자 제안이다. 보관 위치·주기·보존 기간은 '남은 확인 사항'이다.

| 저장소 | 백업 방식 |
| --- | --- |
| SQLite | `better-sqlite3`의 `.backup(destination)`으로 SQLite 온라인 백업을 한다. promise를 돌려주고, 백업 중에도 DB를 계속 쓸 수 있다. 같은 연결이 바꾼 내용은 백업에 반영되지만, 다른 연결이 바꾸면 백업이 처음부터 다시 시작된다. 문서는 온라인 백업을 쓰면 쓰기 연결을 하나로 두라고 권한다. 그래서 쓰기 연결을 하나로 둔다 [better-sqlite3 API][bs3-api], [SQLite 백업 API][sqlite-backup]. `VACUUM INTO`로 운영 중인 DB의 사본을 만드는 방법도 쓸 수 있다 [VACUUM INTO][sqlite-vacuum] |

공통으로 다음을 제안한다.

- 복구 후 프로젝트마다 저장된 그래프의 무결성을 다시 검사하고(`graph validate --project`, ADR-0006), 공정·관계·매핑 수를 백업 시점과 비교한다(AC-24).
- 백업 파일에는 토큰 해시, 세션, 4단계의 Jira 인증값이 들어갈 수 있다. 백업 파일의 접근을 통제한다(F-C09, §7.2).

업데이트 전에 백업하는 것은 [ADR-0002](./0002-deployment-packaging.md) '업데이트·롤백' 원칙으로 채택됐다(2026-10-08). 롤백은 이전 배포물 재설치와 업데이트 전 백업 복구이며, 롤백하면 업데이트 이후 입력한 데이터는 잃는다.

## 검토한 선택지

### 선택지 A: PostgreSQL — 채택하지 않음

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간. DB 서버 연결·마이그레이션·권한 설정이 필요하다 |
| 폐쇄망 반입·운영 부담 | 사내 운영 DB 서비스가 있으면 낮다. 없으면 DB 서버 반입·패치·백업 운영이 추가된다 |
| GUI·CLI 동등성(원칙 7) | 영향 없음. 서버만 접근한다 |
| 관련 요구사항 적합성 | 행 잠금으로 1.1을 구현하기 쉽다. 복합 외래 키·CHECK·CASCADE를 지원한다. 서버 인스턴스를 여러 개 둘 수 있다 |
| 팀 숙련도 | 확인 필요 |

장점: 사내 DB 운영 체계(백업·모니터링)를 활용할 수 있다. 가용성 요구가 커져도 대응 여지가 있다.

단점: 사내 DB 서비스가 없으면 운영 구성 요소가 하나 늘어난다.

결정 시점 판단(2026-10-08): 사내 PostgreSQL은 쓸 수 없다고 확인됐다([ADR-0002](./0002-deployment-packaging.md)). 결정 과정에서 PostgreSQL을 직접 운영하는 안도 검토했으나 SQLite로 정했다. 사유는 기록되지 않았다.

제안 단계에서 적었던 PostgreSQL 구현 방식은 다음과 같다(기록, 채택하지 않음).

| 항목 | PostgreSQL |
| --- | --- |
| 구조 변경 잠금 | 기본 격리 수준(Read Committed)에서 첫 문장으로 프로젝트 행을 `FOR UPDATE`로 잠근다. 이후 `SELECT`는 문장 시작 시점의 스냅숏을 보므로, 앞선 트랜잭션이 커밋한 연결을 읽는다 [격리 수준][pg-iso], [명시적 잠금][pg-lock] |
| 대안 | Serializable 격리로 이상을 감지하고, 직렬화 실패 시 재시도한다. 문서는 이 수준을 쓰는 애플리케이션이 재시도에 대비해야 한다고 밝힌다 |
| 동시성 범위 | 서버 인스턴스 여러 개 가능 |
| 백업 | `pg_dump` 논리 백업과 복구 시험 [pg_dump][pg-dump] |

### 선택지 B: SQLite (WAL, 단일 인스턴스) — 채택

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 낮음. DB가 파일 하나다 |
| 폐쇄망 반입·운영 부담 | 별도 DB 서버가 없다. 드라이버 `better-sqlite3`는 네이티브 애드온이지만 플랫폼별 바이너리가 npm 패키지 안에 들어 있어 내부 npm 미러로 설치할 수 있다(2). 대상 서버 플랫폼이 그 목록에 있는지는 확인이 필요하다 |
| GUI·CLI 동등성(원칙 7) | 영향 없음. 서버만 접근한다 |
| 관련 요구사항 적합성 | 쓰기가 하나씩 처리되므로 1.1 직렬화가 자연스럽다(`BEGIN IMMEDIATE` 필수). 외래 키를 연결마다 켜야 한다. 고가용성과 수평 확장은 없다 |
| 팀 숙련도 | 확인 필요 |

장점: 구성 요소가 가장 적다. 백업이 파일 사본으로 단순하다.

단점: 서버 프로세스 하나에 묶인다. 네트워크 파일 시스템 위에서 쓸 수 없다.

### 참고: 검토했으나 제안하지 않은 동시성 방식

| 방식 | 제안하지 않은 이유 |
| --- | --- |
| 행 단위 낙관적 잠금만 사용 | A → B와 B → A 동시 추가를 막지 못한다(배경의 첫 표) |
| 프로젝트 전체에 버전 하나만 두고 모든 변경을 감지 | 노드 이동, 상태 변경, Jira 새로고침까지 서로 충돌로 처리되어 불필요한 `CONFLICT`가 쏟아진다 |

## 트레이드오프

- 같은 프로젝트의 구조 변경은 한 번에 하나씩 처리된다. SQLite에서는 쓰기가 DB 전체에서 하나씩 처리되므로 다른 프로젝트의 쓰기도 서로 기다린다. 동시 편집자가 적다면 문제가 없을 것으로 보지만, 예상 규모는 확인이 필요하다.
- `better-sqlite3`는 동기식 API라 쿼리가 실행되는 동안 Node.js 이벤트 루프가 막힌다. 그동안 같은 서버 프로세스의 다른 요청(읽기와 정적 자산 응답 포함)도 기다린다. 프로젝트 그래프가 작다는 가정에 기대며, 이것도 규모 확인 대상이다.
- 검증할 때마다 프로젝트 그래프 전체를 읽는다. 프로젝트당 공정 수가 작다는 가정에 기대며, 이것도 규모 확인 대상이다.
- 기대 버전 생략을 허용했으므로 스크립트가 쓰기 쉬운 대신, 생략한 요청은 덮어쓰기 감지가 약해진다(1.3).
- 리포지토리 계층으로 감싸도 DB별 잠금 방식은 다르다. 저장소를 바꾸면 잠금 코드와 시험은 다시 작성해야 한다.
- 상위가 있는 공정의 실행 상태 변경을 프로젝트 잠금 안에서 처리하므로 상위 자동 완료를 놓치지 않는 대신, 상태 변경도 구조 변경과 같은 잠금을 기다린다(1.7). SQLite에서는 모든 쓰기가 이미 하나씩 처리되므로 이 규칙 때문에 새로 생기는 대기는 없다.
- 상속된 선행 조건과 하위 집계를 조회 시 계산하면 저장 불일치가 없는 대신, 조회마다 조상 경로를 올라간다. 깊이 제한이 없으므로 예상 깊이도 규모 확인 대상이다.

## 결과

쉬워지는 것:

- AC-17(같은 공정 동시 수정)과 AC-18(A → B·B → A 동시 추가)을 시험 가능한 규칙으로 구현할 수 있다.
- 오류 분류의 `CONFLICT`와 CLI 종료 코드 5의 의미가 정해진다(ADR-0006, ADR-0007).
- dry-run과 실제 실행을 `graph_revision`으로 묶을 수 있다(ADR-0006).
- AC-25(상위 자동 완료), AC-27(다른 층 연결 거부), AC-29(자손을 상위로 지정 거부), AC-32(연결이 남은 공정의 상위 변경 거부)를 같은 잠금·검증 경로에서 시험할 수 있다.
- SQLite 단일 writer라 1.1의 직렬화와 1.7의 상태 변경 잠금이 `BEGIN IMMEDIATE`로 함께 충족된다.
- 별도 DB 서버 없이 데이터 디렉터리의 파일 하나로 운영한다(ADR-0002).

어려워지는 것:

- 모든 구조 변경 경로(단건 API, 변경 묶음, 이후 템플릿 적용)가 같은 잠금·검증 경로를 타도록 강제해야 한다(F-D06).
- 좌표와 Jira 조회 결과를 별도 테이블로 분리하는 설계가 필요하다.
- 계층이 있으면 실행 상태 변경 경로도 잠금 경로를 타야 한다(1.7).
- 동기식 API라 오래 걸리는 쿼리 하나가 서버 전체의 응답을 늦춘다.
- 고가용성과 수평 확장이 없다.

다시 검토할 시점:

- 프로젝트당 공정 수나 동시 편집자가 예상보다 커져 잠금 대기가 체감될 때.
- 동기식 쿼리로 서버 응답 지연이 체감될 때.
- 계층 깊이가 깊어져 조회 시 계산(상속된 선행 조건, 하위 집계)이 느려질 때.
- 고가용성 요구가 생겨 SQLite 단일 인스턴스로 부족할 때.
- 대상 서버 플랫폼이 `better-sqlite3` 미리 빌드된 바이너리 목록에 없을 때.
- 프로젝트를 가로지르는 연결(PRD §6.2 하단, 이후 검토)을 도입할 때. 검증 범위를 프로젝트보다 넓혀야 한다. SQLite는 쓰기를 이미 DB 전체에서 하나씩 처리한다.
