## 배경

- N-06: 웹과 CLI의 인증·권한 검사와 서버 측 검증을 일관되게 적용한다. 이 ADR 작성 당시(2026-10-07) 구체적인 사내 인증 연동 방식과 권한 모델은 미정이었다.
- §13-3: 공개 열람·수정 범위를 임의로 가정하지 않는다.
- §4.1: 사용자 구분은 '그대로 권한 역할을 확정한 것은 아니다'. 에이전트는 '사용자가 허용한 범위에서' 동작한다.
- F-C09: 인증 정보를 출력·오류·일반 데이터에 노출하지 않고, 에이전트 작업에 필요한 권한만 사용한다.
- N-02: 외부 인증을 필수로 요구하지 않는다.

§13-3이 공개 열람·수정 범위를 임의로 가정하지 못하게 하므로, 초기 핵심 착수 전에 인증·권한 범위를 결정해야 한다. N-06은 웹과 CLI에 같은 인증·권한 검사를 적용하라고 한다. 이 ADR 작성 당시 PRD §11 표 아래 문단은 최소 인증을 초기 핵심에 넣는 것을 제안으로 적었고, 채택 전이었다. 2026-10-08 이 ADR이 채택되어 최소 인증의 방식과 권한 범위가 정해졌다(아래 '결정'). 현재 PRD §11 문단, §13-3, N-06 비고는 이 결정을 반영했다.

이 결정에 걸려 있는 것은 다음과 같다.

| 걸려 있는 것 | 근거 |
| --- | --- |
| 모든 API의 인증·권한 미들웨어 | N-06 |
| GUI 로그인 흐름과 세션 | N-06 |
| CLI의 인증값 전달 방식 | F-C09, §13-10 |
| 권한 부족 오류와 종료 코드 | F-C05, ADR-0006·ADR-0007 |
| 생성·수정 정보에 기록할 행위자 식별 | §7.1 |
| 에이전트를 사람 세션으로 돌릴지, 범위를 줄인 토큰으로 돌릴지 | F-C06, F-C09 |

Jira 인증 주체(공용 서비스 계정인지 사용자별 토큰인지)는 PRD §6.7과 §13-6의 쟁점이다. 이 ADR의 범위 밖이지만 사용자 모델과 연계된다. 아래 '연계: Jira 인증 주체'에 영향만 적는다.

## 결정

2026-10-08 결정권자가 선택지 A(Tevro 로컬 계정 + 개인 액세스 토큰)를 채택했다. 결정권자에게 보인 선택지 A의 설명은 'Tevro 자체 계정(Argon2id) + 개인 액세스 토큰. 사용자 ID와 인증 수단을 분리해 나중에 사내 디렉터리를 붙일 수 있게 한다'였다. 그래서 Argon2id 비밀번호 저장과 사용자·인증 수단 분리도 이 결정의 범위다.

| 항목 | 결정 |
| --- | --- |
| 1. 인증 방식 | 선택지 A: Tevro 로컬 계정(비밀번호는 Argon2id) + 개인 액세스 토큰. 사용자 ID와 인증 수단을 분리해 사내 디렉터리(선택지 B)를 나중에 붙일 수 있게 한다 |
| 2. 권한 범위 | 인스턴스 전체의 세 역할(열람자·편집자·관리자)만 둔다. 프로젝트별 열람 제한(기밀 프로젝트)은 필요 없다. 프로젝트 멤버십은 두지 않는다. 필요해지면 프로젝트 멤버십을 역할 위에 더한다('다시 검토할 시점') |
| 3. 템플릿 삭제, 프로젝트 삭제·보관 | 관리자만 한다. 편집자는 공정·연결 삭제까지만 한다 |
| 4. AI 에이전트 | 사람이 자기 계정으로 범위를 줄인 토큰(`read` 등)을 발급해 에이전트에 준다. 에이전트 전용 계정(서비스 계정)은 두지 않는다 |
| 공통 구조 | 제안대로 채택. 서버 저장 세션 + HttpOnly·Secure·SameSite 쿠키 + CSRF 방어, PAT의 `read`/`read-write` 범위와 역할의 교집합, 만료일 필수, 해시만 저장, `tevro_pat_` 접두사로 로그 가림, 토큰은 명령행 인자로 받지 않고 환경변수·권한 600 파일로만, 최초 관리자는 서버 호스트 관리 명령으로, 변경 기록에 사용자 ID와 토큰 ID |

결정권자가 명시적으로 답한 범위는 1~4이고, 공통 구조에는 별도 수정 요청이 없었다. 공통 구조는 결정 과정에서 결정권자에게 함께 보였고 고칠 부분을 지적받지 않았으므로, 제안 그대로 채택한 것으로 기록한다. 선택 사유는 따로 기록되지 않았다. 제안 단계의 판단은 '검토한 선택지'에 그대로 둔다.

제안 단계에서는 '선택지 A로 시작하고, 선택지 B를 나중에 붙일 수 있게 사용자 ID와 인증 공급자를 분리하는 것'을 제안했다(기록). 결정은 이 방향과 같다. 제안 단계에서 결정 필요로 둔 것 중 프로젝트별 열람 제한(2), 편집자의 템플릿 삭제·프로젝트 삭제·보관(3), 에이전트 전용 계정(4)이 이번에 정해졌다.

이번 결정에서 정하지 않은 것은 다음과 같다. 모두 '남은 확인 사항'에 둔다.

- 토큰 만료 기본값·최대값, 세션 유휴 만료·절대 만료 시간.
- 비밀번호 정책과 재설정 절차, 로그인 실패 제한을 둘지와 그 기준.
- Jira 연동 설정(F-J01) 권한. 관리자만 하는 것은 제안이다(권한 표).
- 생성·수정 정보의 행위자를 공정 단위로도 남길지(§7.1).
- HTTPS 종단 위치([ADR-0002](./0002-deployment-packaging.md)).
- 사내 LDAP/AD·OIDC 연동 여부. 나중에 선택지 B를 추가할 때 정한다.
- Jira 인증 주체. 이 ADR 범위 밖이며 PRD §6.7, §13-6에서 정한다.

### 공통 구조 — 제안대로 채택(A와 B 모두에 적용)

**사용자와 인증 공급자 분리**

- 사용자는 `usr_` 식별자([ADR-0005](./0005-identifiers-and-deletion.md))를 가진다.
- 인증 수단(로컬 비밀번호, LDAP·OIDC 주체)은 사용자와 분리한 별도 테이블에 (공급자, 공급자 내 식별자)로 연결한다.
- 그래서 로컬 계정으로 시작한 뒤 사내 디렉터리 연동을 붙여도 사용자 ID와 기록이 바뀌지 않는다.

**권한: 인스턴스 단위 세 역할**

| 작업 | 열람자 | 편집자 | 관리자 |
| --- | --- | --- | --- |
| 프로젝트·공정·관계·상태 조회 | 가능 | 가능 | 가능 |
| 프로젝트·공정·관계·상태 생성·수정, 공정·관계 삭제 | 불가 | 가능 | 가능 |
| 템플릿 작성·수정(재사용 단계) | 불가 | 가능 | 가능 |
| 템플릿 삭제(F-T10) | 불가 | 불가(2026-10-08 결정) | 가능 |
| 프로젝트 삭제·보관(PRD §13-14) | 불가 | 불가(2026-10-08 결정) | 가능 |
| 본인 개인 액세스 토큰 발급·폐기 | read 범위만 | 가능 | 가능 |
| 사용자·역할 관리, 다른 사용자의 토큰 폐기 | 불가 | 불가 | 가능 |
| Jira 연동 설정(F-J01, 4단계) | 불가 | 불가 | 가능(제안, 결정 필요) |

편집자는 공정·연결 삭제까지 한다. 템플릿 삭제와 프로젝트 삭제·보관은 관리자만 한다(2026-10-08 결정). 프로젝트 삭제·보관을 제공할지와 그 방식은 PRD §13-14와 [ADR-0005](./0005-identifiers-and-deletion.md)에서 정한다.

복잡한 역할 체계는 초기 범위 밖이다(PRD §9). 제안 단계에서는 프로젝트별 열람 제한(기밀 프로젝트)이 필요한지 이해관계자에게 확인한다고 적었다. 2026-10-08 결정권자가 필요 없음으로 결정했다. 인스턴스 역할만 두고 프로젝트 멤버십은 두지 않는다. 필요해지면 인스턴스 역할 위에 프로젝트 멤버십을 더한다('다시 검토할 시점'). 그때 목록 조회 필터링과, 권한 없는 프로젝트에 `FORBIDDEN`을 줄지 `NOT_FOUND`로 존재를 숨길지도 함께 정한다.

**웹 세션**

- 로그인 성공 시 서버 저장 세션을 만들고 세션 쿠키를 발급한다. 쿠키에는 HttpOnly, Secure, SameSite 속성을 붙인다. Secure 속성은 HTTPS를 전제로 하므로 TLS 종단 위치를 [ADR-0002](./0002-deployment-packaging.md)에서 확인한다(남은 확인 사항).
- 상태를 바꾸는 요청은 CSRF 방어 토큰을 확인한다.
- 세션을 DB에 두어 서버 재시작 후에도 유지하고, 관리자가 폐기할 수 있게 한다.
- 유휴 만료와 절대 만료 시간은 결정 필요.

**CLI·에이전트용 개인 액세스 토큰(PAT)**

| 항목 | 내용 |
| --- | --- |
| 발급 | 웹 화면에서 본인이 발급한다. 이름(용도), 범위, 만료일을 지정한다. 값은 발급할 때 한 번만 보여 준다 |
| 범위 | `read` 또는 `read-write`. 실제 권한은 사용자 역할과 토큰 범위의 교집합이다. 역할이 낮아지거나 계정이 비활성화되면 토큰에도 즉시 반영된다 |
| 저장 | 서버에는 해시만 저장한다. 토큰은 충분히 긴 무작위 값이므로 빠른 해시로 충분하다고 보며, 비밀번호와 다른 해시 방식을 쓴다 |
| 형식 | 알아볼 수 있는 고정 접두사(예: `tevro_pat_`) + 무작위 값. 로그와 오류 출력에서 접두사로 찾아 가린다(AC-20) |
| 만료·폐기 | 만료일이 반드시 있다. 기본값과 최대값은 결정 필요. 본인과 관리자가 폐기할 수 있다. 마지막 사용 시각을 보여 준다 |
| 식별 | 토큰마다 `tok_` 식별자를 둔다. 비밀값과 다르며 화면·로그에 표시해도 된다 |
| 행위자 기록 | 생성·수정 정보(§7.1)의 행위자 필드에 사용자 ID와 토큰 ID를 함께 남긴다. 사람의 웹 작업과 에이전트 작업을 구분할 수 있다. PRD §7.1에는 프로젝트의 생성·수정 정보만 있고 공정 항목에는 없으므로, 공정 단위로도 남길지는 결정 필요. 체계적인 변경 이력은 후속 검토 대상이다(F-M08) |
| 범위 확장 | 프로젝트 한정 토큰은 후속 검토로 둔다 |

에이전트 전용 계정(사람이 아닌 서비스 계정)은 두지 않기로 결정했다(2026-10-08). 제안 단계에서는 결정 필요로 두고, 초기 제안으로 지금의 방식을 적었다(기록). 사람이 자기 계정으로 범위를 줄인 토큰을 발급해 에이전트에 준다. `read` 토큰으로 F-C06·F-C09의 최소 권한을 구현할 수 있다.

**CLI 인증값 전달**

- 토큰을 명령행 인자로 받지 않는다. 프로세스 목록과 셸 이력에 남기 때문이다(F-C09).
- 환경변수 또는 권한 600 설정 파일로만 받는다. 우선순위와 이름은 [ADR-0007](./0007-cli-contract.md)에서 정한다.
- 서버는 `Authorization` 헤더를 로그에 남기지 않는다. 인증 실패 오류 메시지에 받은 값을 되돌려 보내지 않는다(AC-20).

### 선택지 A의 추가 구성: Tevro 로컬 계정

- 비밀번호는 느린 해시인 Argon2id로 저장한다(2026-10-08 결정. 결정권자에게 보인 선택지 A 설명에 포함). OWASP는 Argon2id를 우선 권고하고 scrypt를 다음 선택지로 둔다. [OWASP Password Storage][owasp-pw]
- Node.js에는 `crypto.argon2`·`crypto.argon2Sync`(v24.7.0 추가)와 `crypto.scrypt`(v10.5.0 추가)가 내장되어 있다. 2026-10-08 Node.js 현재 문서(v26)를 다시 확인했다. `crypto.argon2`·`crypto.argon2Sync` 절에는 실험적(Experimental) 표시가 없다. [ADR-0001](./0001-tech-stack.md)이 Node.js 26을 채택했으므로 내장 `crypto.argon2`를 쓸 수 있다. 내장 함수를 쓰면 폐쇄망에 네이티브 애드온을 반입하지 않아도 된다. [Node.js crypto][node-crypto]
- 제안 단계 원문(기록): '채택할 Node.js 버전에서의 지원과 안정성 등급은 채택 전 확인한다.' 위의 2026-10-08 확인으로 갈음한다.
- 최초 관리자는 서버 호스트에서 실행하는 관리 명령으로 만든다(예: 비밀번호를 표준 입력으로 받는 `tevro-server admin create`). '먼저 접속한 사람이 관리자가 되는' 웹 화면은 두지 않는다. 설치 직후 다른 사람이 선점할 수 있기 때문이다. 공통 구조로 결정권자에게 보였고 제안대로 채택했다(2026-10-08).
- 로그인 실패 횟수 제한을 두는 것을 제안한다. 결정권자가 이 항목에 따로 답하지 않았으므로 작성자 제안으로 둔다. 로그인 실패 제한을 둘지와 그 기준, 비밀번호 정책, 재설정 절차(관리자 재설정 등)는 결정 필요.

## 검토한 선택지

### 선택지 A: Tevro 로컬 계정 + 개인 액세스 토큰 — 채택

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간. 비밀번호 저장, 세션, 토큰 발급·폐기 화면을 직접 만든다 |
| 폐쇄망 반입·운영 부담 | 외부·사내 인증 시스템이 필요 없다(N-02, AC-14). 계정 생성·비활성화는 Tevro 관리자가 직접 한다 |
| GUI·CLI 동등성(원칙 7) | 웹 세션과 CLI 토큰이 같은 서버 권한 계층을 통과한다(N-06) |
| 관련 요구사항 적합성 | §13-3, N-06, F-C09, AC-20을 충족할 수 있다. 사내 계정 수명주기(퇴사·이동)와는 따로 관리된다 |
| 팀 숙련도 | 확인 필요 |

장점: 가장 빨리 착수할 수 있다. 사내 연동 환경 확인을 기다리지 않는다.

단점: 사용자가 비밀번호를 하나 더 관리한다. 퇴사자 계정 정리를 Tevro에서 따로 해야 한다.

### 선택지 B: 사내 LDAP/AD 또는 망 내 OIDC + 같은 토큰 체계 — 채택하지 않음(나중에 추가할 수 있게 구조만 대비)

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간~높음. 사내 디렉터리·IdP 연동, 그룹→역할 매핑, 장애 시 대비책이 필요하다 |
| 폐쇄망 반입·운영 부담 | 망 안의 시스템이라 외부 인터넷 의존은 아니다. 다만 연동 승인, 서비스 계정, 인증서 확인이 필요하다 |
| GUI·CLI 동등성(원칙 7) | 웹 로그인만 바뀌고 CLI는 같은 토큰 체계를 쓴다 |
| 관련 요구사항 적합성 | 계정 수명주기를 사내 표준에 맡길 수 있다. 사내 IdP 장애 때 Tevro 로그인이 막히므로 로컬 비상 관리자 계정을 남겨야 한다 |
| 팀 숙련도 | 확인 필요 |

장점: 별도 비밀번호가 없다. 퇴사·이동이 자동 반영될 수 있다.

단점: 연동 환경을 먼저 확인해야 해서 착수가 늦어질 수 있다.

결정 시점 판단(2026-10-08): 채택하지 않았다. 사유는 기록되지 않았다. 사용자 ID와 인증 수단을 분리해(공통 구조) 나중에 추가할 수 있게 구조만 대비한다. 사내 LDAP/AD·OIDC 연동 여부와 연동 승인 절차는 '남은 확인 사항'이다.

### 선택지 C: 인증 없음(망 접근 통제에만 의존) — 채택하지 않음

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 가장 낮음 |
| 폐쇄망 반입·운영 부담 | 없음 |
| GUI·CLI 동등성(원칙 7) | 형식상 같지만 권한 검사가 없다 |
| 관련 요구사항 적합성 | 망 접근 통제만으로 공개 범위를 정하는 것은 §13-3('공개 열람·수정 범위를 임의로 가정하지 않는다')에 맞지 않는다. N-06의 인증·권한 검사, F-C05의 권한 부족, F-C09의 최소 권한도 의미가 없어진다 |
| 팀 숙련도 | 해당 없음 |

제안하지 않는다. 이해관계자 확인 전의 판단이다. 이해관계자가 망 접근 통제만으로 충분하다고 확인하면 다시 검토한다.

결정 시점 판단(2026-10-08): 결정권자가 선택지 A를 채택했으므로 채택하지 않았다.

## 연계: Jira 인증 주체

PRD §6.7은 공용 서비스 계정과 사용자별 개인 액세스 토큰을 비교하며 결정 필요로 둔다. 이 ADR에 주는 영향은 다음과 같다.

| Jira 쪽 선택 | 이 ADR에 주는 영향 |
| --- | --- |
| 공용 서비스 계정 | Tevro 권한이 Jira 정보 노출 범위를 사실상 결정한다. Jira 권한이 없는 Tevro 사용자도 이슈 제목·상태를 볼 수 있다(PRD §6.7) |
| 사용자별 Jira 토큰 | Tevro 사용자와 Jira 사용자를 연결해야 한다. 사용자별 외부 인증값을 일반 데이터와 분리해 보관해야 한다(§7.2, F-C09) |

어느 쪽이든 Jira 인증값은 Tevro 토큰과 별도로 저장하고, 브라우저 번들·CLI 출력·프로젝트 데이터에 넣지 않는다(OSS §6.4, §11.2).

## 트레이드오프

- A는 빨리 시작하는 대신 계정 관리 부담을 Tevro에 남긴다. B는 계정 관리를 사내 표준에 맡기는 대신 착수 전 확인할 것이 많다.
- 인스턴스 단위 역할은 단순한 대신 프로젝트별 비공개가 필요해지면 권한 검사 위치가 늘어난다.
- 토큰 만료를 짧게 하면 안전하지만 에이전트 운영자가 자주 재발급해야 한다.
- 환경변수 전달은 편하지만 같은 사용자의 다른 프로세스나 하위 프로세스에 노출될 수 있다. 설정 파일은 권한 관리가 필요하다.
- 에이전트 전용 계정을 두지 않으므로 에이전트 토큰은 발급한 사람의 계정과 역할에 묶인다. 그 사람의 역할이 낮아지거나 계정이 비활성화되면 에이전트 토큰에도 즉시 반영된다(PAT '범위').

## 결과

쉬워지는 것:

- 모든 API에 같은 인증·권한 계층을 적용할 수 있다(N-06).
- `UNAUTHENTICATED`·`FORBIDDEN` 오류와 CLI 종료 코드 4의 의미가 정해진다(ADR-0006, ADR-0007).
- 생성·수정 정보의 행위자로 사람과 에이전트(토큰)를 구분해 남길 수 있다(§7.1).

어려워지는 것:

- 로그인, 토큰 발급·폐기, 사용자 관리 화면이 초기 핵심 범위에 들어온다.
- 로그·오류에서 인증값을 가리는 규칙을 시험으로 지켜야 한다(AC-20).

다시 검토할 시점:

- 사내 LDAP/AD 또는 OIDC 연동 환경이 확인될 때(선택지 B 추가).
- 기밀 프로젝트 열람 제한이 필요해질 때(프로젝트 멤버십).
- Jira 인증 주체가 결정될 때(PRD §13-6).
