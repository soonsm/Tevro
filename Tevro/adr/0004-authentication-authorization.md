# ADR-0004: 사용자 인증·최소 권한과 에이전트 토큰

- 상태: 제안 (Proposed)
- 작성일: 2026-10-07
- 결정권자: 미정 — 프로젝트 담당자가 지정
- 관련 문서:

  - 연계 PRD 쟁점: §6.7 'Jira 인증 주체 — 결정 필요', §13-6
  - OSS: [오픈소스와 구현 경계](../open-source-components.md) §6.4 마지막 문단, §9 '인증·권한·입력 검증', §11.2
  - 선행 ADR: [ADR-0001](./0001-tech-stack.md), [ADR-0003](./0003-storage-and-concurrency.md)
  - 병렬 ADR: [ADR-0005](./0005-identifiers-and-deletion.md)

## 배경

- N-06: 웹과 CLI의 인증·권한 검사와 서버 측 검증을 일관되게 적용한다. 구체적인 사내 인증 연동 방식과 권한 모델은 미정이다.
- §13-3: 공개 열람·수정 범위를 임의로 가정하지 않는다.
- §4.1: 사용자 구분은 '그대로 권한 역할을 확정한 것은 아니다'. 에이전트는 '사용자가 허용한 범위에서' 동작한다.
- F-C09: 인증 정보를 출력·오류·일반 데이터에 노출하지 않고, 에이전트 작업에 필요한 권한만 사용한다.
- N-02: 외부 인증을 필수로 요구하지 않는다.

§13-3이 공개 열람·수정 범위를 임의로 가정하지 못하게 하므로, 초기 핵심 착수 전에 인증·권한 범위를 결정해야 한다. N-06은 웹과 CLI에 같은 인증·권한 검사를 적용하라고 한다. PRD §11 표 아래 문단은 최소 인증을 초기 핵심에 넣는 것을 제안으로 적는다. 아직 채택되지 않았다.

이 결정에 걸려 있는 것은 다음과 같다.

| 걸려 있는 것 | 근거 |
| --- | --- |
| 모든 API의 인증·권한 미들웨어 | N-06 |
| GUI 로그인 흐름과 세션 | N-06 |
| CLI의 인증값 전달 방식 | F-C09, §13-10 |
| 권한 부족 오류와 종료 코드 | F-C05, ADR-0006·ADR-0007 |
| 생성·수정 정보에 기록할 행위자 식별 | §7.1 |
| 에이전트를 사람 세션으로 돌릴지, 범위를 줄인 토큰으로 돌릴지 | F-C06, F-C09 |

Jira 인증 주체(공용 서비스 계정인지 사용자별 토큰인지)는 PRD §6.7과 §13-6의 쟁점이다. 이 ADR의 범위 밖이지만 사용자 모델과 연계된다. 아래 '연계: Jira 인증 주체'에 영향만 적는다.

## 제안하는 결정

선택지 A(Tevro 로컬 계정 + 개인 액세스 토큰)로 시작하고, 선택지 B를 나중에 붙일 수 있게 사용자 ID와 인증 공급자를 분리하는 것을 제안한다.

### 공통 구조 — A와 B 모두에 적용

**사용자와 인증 공급자 분리**

- 사용자는 `usr_` 식별자([ADR-0005](./0005-identifiers-and-deletion.md))를 가진다.
- 인증 수단(로컬 비밀번호, LDAP·OIDC 주체)은 사용자와 분리한 별도 테이블에 (공급자, 공급자 내 식별자)로 연결한다.
- 그래서 로컬 계정으로 시작한 뒤 사내 디렉터리 연동을 붙여도 사용자 ID와 기록이 바뀌지 않는다.

**권한: 인스턴스 단위 세 역할로 시작**

| 작업 | 열람자 | 편집자 | 관리자 |
| --- | --- | --- | --- |
| 프로젝트·공정·관계·상태 조회 | 가능 | 가능 | 가능 |
| 프로젝트·공정·관계·상태 생성·수정·삭제 | 불가 | 가능 | 가능 |
| 템플릿 작성·수정(재사용 단계) | 불가 | 가능 | 가능 |
| 템플릿 삭제(F-T10) | 불가 | 결정 필요 | 가능 |
| 프로젝트 삭제·보관(PRD §13-14) | 불가 | 결정 필요 | 가능 |
| 본인 개인 액세스 토큰 발급·폐기 | read 범위만 | 가능 | 가능 |
| 사용자·역할 관리, 다른 사용자의 토큰 폐기 | 불가 | 불가 | 가능 |
| Jira 연동 설정(F-J01, 4단계) | 불가 | 불가 | 가능(제안) |

복잡한 역할 체계는 초기 범위 밖이다(PRD §9). 프로젝트별 열람 제한(기밀 프로젝트)이 필요한지는 이해관계자에게 확인한다. 필요하면 인스턴스 역할 위에 프로젝트 멤버십을 더한다. 이 경우 목록 조회 필터링과, 권한 없는 프로젝트에 `FORBIDDEN`을 줄지 `NOT_FOUND`로 존재를 숨길지도 함께 정한다.

**웹 세션**

- 로그인 성공 시 서버 저장 세션을 만들고 세션 쿠키를 발급한다. 쿠키에는 HttpOnly, Secure, SameSite 속성을 붙인다. Secure 속성은 HTTPS를 전제로 하므로 TLS 종단 위치를 [ADR-0002](./0002-deployment-packaging.md)에서 확인한다.
- 상태를 바꾸는 요청은 CSRF 방어 토큰을 확인한다.
- 세션을 DB에 두어 서버 재시작 후에도 유지하고, 관리자가 폐기할 수 있게 한다.
- 유휴 만료와 절대 만료 시간은 결정 필요.

**CLI·에이전트용 개인 액세스 토큰(PAT)**

| 항목 | 제안 |
| --- | --- |
| 발급 | 웹 화면에서 본인이 발급한다. 이름(용도), 범위, 만료일을 지정한다. 값은 발급할 때 한 번만 보여 준다 |
| 범위 | `read` 또는 `read-write`. 실제 권한은 사용자 역할과 토큰 범위의 교집합이다. 역할이 낮아지거나 계정이 비활성화되면 토큰에도 즉시 반영된다 |
| 저장 | 서버에는 해시만 저장한다. 토큰은 충분히 긴 무작위 값이므로 빠른 해시로 충분하다고 보며, 비밀번호와 다른 해시 방식을 쓴다 |
| 형식 | 알아볼 수 있는 고정 접두사(예: `tevro_pat_`) + 무작위 값. 로그와 오류 출력에서 접두사로 찾아 가린다(AC-20) |
| 만료·폐기 | 만료일이 반드시 있다. 기본값과 최대값은 결정 필요. 본인과 관리자가 폐기할 수 있다. 마지막 사용 시각을 보여 준다 |
| 식별 | 토큰마다 `tok_` 식별자를 둔다. 비밀값과 다르며 화면·로그에 표시해도 된다 |
| 행위자 기록 | 생성·수정 정보(§7.1)의 행위자 필드에 사용자 ID와 토큰 ID를 함께 남긴다. 사람의 웹 작업과 에이전트 작업을 구분할 수 있다. PRD §7.1에는 프로젝트의 생성·수정 정보만 있고 공정 항목에는 없으므로, 공정 단위로도 남길지는 결정 필요. 체계적인 변경 이력은 후속 검토 대상이다(F-M08) |
| 범위 확장 | 프로젝트 한정 토큰은 후속 검토로 둔다 |

에이전트 전용 계정(사람이 아닌 서비스 계정)을 둘지는 결정 필요. 초기 제안은 사람이 자기 계정으로 범위를 줄인 토큰을 발급해 에이전트에 주는 방식이다. `read` 토큰으로 F-C06·F-C09의 최소 권한을 구현할 수 있다.

**CLI 인증값 전달**

- 토큰을 명령행 인자로 받지 않는다. 프로세스 목록과 셸 이력에 남기 때문이다(F-C09).
- 환경변수 또는 권한 600 설정 파일로만 받는다. 우선순위와 이름은 [ADR-0007](./0007-cli-contract.md)에서 정한다.
- 서버는 `Authorization` 헤더를 로그에 남기지 않는다. 인증 실패 오류 메시지에 받은 값을 되돌려 보내지 않는다(AC-20).

### 선택지 A의 추가 구성: Tevro 로컬 계정

- 비밀번호는 느린 해시로 저장한다. OWASP는 Argon2id를 우선 권고하고 scrypt를 다음 선택지로 둔다. [OWASP Password Storage][owasp-pw]
- Node.js에는 `crypto.scrypt`(v10.5.0 추가)와 `crypto.argon2`(v24.7.0 추가)가 내장되어 있다. 내장 함수를 쓰면 폐쇄망에 네이티브 애드온을 반입하지 않아도 된다. 채택할 Node.js 버전에서의 지원과 안정성 등급은 채택 전 확인한다. [Node.js crypto][node-crypto]
- 최초 관리자는 서버 호스트에서 실행하는 관리 명령으로 만든다(예: 비밀번호를 표준 입력으로 받는 `tevro-server admin create`). '먼저 접속한 사람이 관리자가 되는' 웹 화면은 두지 않는다. 설치 직후 다른 사람이 선점할 수 있기 때문이다.
- 로그인 실패 횟수 제한을 둔다. 비밀번호 정책과 재설정 절차(관리자 재설정 등)는 결정 필요.

## 검토한 선택지

### 선택지 A: Tevro 로컬 계정 + 개인 액세스 토큰

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간. 비밀번호 저장, 세션, 토큰 발급·폐기 화면을 직접 만든다 |
| 폐쇄망 반입·운영 부담 | 외부·사내 인증 시스템이 필요 없다(N-02, AC-14). 계정 생성·비활성화는 Tevro 관리자가 직접 한다 |
| GUI·CLI 동등성(원칙 7) | 웹 세션과 CLI 토큰이 같은 서버 권한 계층을 통과한다(N-06) |
| 관련 요구사항 적합성 | §13-3, N-06, F-C09, AC-20을 충족할 수 있다. 사내 계정 수명주기(퇴사·이동)와는 따로 관리된다 |
| 팀 숙련도 | 확인 필요 |

장점: 가장 빨리 착수할 수 있다. 사내 연동 환경 확인을 기다리지 않는다.

단점: 사용자가 비밀번호를 하나 더 관리한다. 퇴사자 계정 정리를 Tevro에서 따로 해야 한다.

### 선택지 B: 사내 LDAP/AD 또는 망 내 OIDC + 같은 토큰 체계

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간~높음. 사내 디렉터리·IdP 연동, 그룹→역할 매핑, 장애 시 대비책이 필요하다 |
| 폐쇄망 반입·운영 부담 | 망 안의 시스템이라 외부 인터넷 의존은 아니다. 다만 연동 승인, 서비스 계정, 인증서 확인이 필요하다 |
| GUI·CLI 동등성(원칙 7) | 웹 로그인만 바뀌고 CLI는 같은 토큰 체계를 쓴다 |
| 관련 요구사항 적합성 | 계정 수명주기를 사내 표준에 맡길 수 있다. 사내 IdP 장애 때 Tevro 로그인이 막히므로 로컬 비상 관리자 계정을 남겨야 한다 |
| 팀 숙련도 | 확인 필요 |

장점: 별도 비밀번호가 없다. 퇴사·이동이 자동 반영될 수 있다.

단점: 연동 환경을 먼저 확인해야 해서 착수가 늦어질 수 있다.

### 선택지 C: 인증 없음(망 접근 통제에만 의존)

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 가장 낮음 |
| 폐쇄망 반입·운영 부담 | 없음 |
| GUI·CLI 동등성(원칙 7) | 형식상 같지만 권한 검사가 없다 |
| 관련 요구사항 적합성 | 망 접근 통제만으로 공개 범위를 정하는 것은 §13-3('공개 열람·수정 범위를 임의로 가정하지 않는다')에 맞지 않는다. N-06의 인증·권한 검사, F-C05의 권한 부족, F-C09의 최소 권한도 의미가 없어진다 |
| 팀 숙련도 | 해당 없음 |

제안하지 않는다. 이해관계자 확인 전의 판단이다. 이해관계자가 망 접근 통제만으로 충분하다고 확인하면 다시 검토한다.

## 연계: Jira 인증 주체

PRD §6.7은 공용 서비스 계정과 사용자별 개인 액세스 토큰을 비교하며 결정 필요로 둔다. 이 ADR에 주는 영향은 다음과 같다.

| Jira 쪽 선택 | 이 ADR에 주는 영향 |
| --- | --- |
| 공용 서비스 계정 | Tevro 권한이 Jira 정보 노출 범위를 사실상 결정한다. Jira 권한이 없는 Tevro 사용자도 이슈 제목·상태를 볼 수 있다(PRD §6.7) |
| 사용자별 Jira 토큰 | Tevro 사용자와 Jira 사용자를 연결해야 한다. 사용자별 외부 인증값을 일반 데이터와 분리해 보관해야 한다(§7.2, F-C09) |

어느 쪽이든 Jira 인증값은 Tevro 토큰과 별도로 저장하고, 브라우저 번들·CLI 출력·프로젝트 데이터에 넣지 않는다(OSS §6.4, §11.2).

## 트레이드오프

- A는 빨리 시작하는 대신 계정 관리 부담을 Tevro에 남긴다. B는 계정 관리를 사내 표준에 맡기는 대신 착수 전 확인할 것이 많다.
- 인스턴스 단위 역할은 단순한 대신 프로젝트별 비공개가 필요해지면 권한 검사 위치가 늘어난다.
- 토큰 만료를 짧게 하면 안전하지만 에이전트 운영자가 자주 재발급해야 한다.
- 환경변수 전달은 편하지만 같은 사용자의 다른 프로세스나 하위 프로세스에 노출될 수 있다. 설정 파일은 권한 관리가 필요하다.

## 결과

쉬워지는 것:

- 모든 API에 같은 인증·권한 계층을 적용할 수 있다(N-06).
- `UNAUTHENTICATED`·`FORBIDDEN` 오류와 CLI 종료 코드 4의 의미가 정해진다(ADR-0006, ADR-0007).
- 생성·수정 정보의 행위자로 사람과 에이전트(토큰)를 구분해 남길 수 있다(§7.1).

어려워지는 것:

- 로그인, 토큰 발급·폐기, 사용자 관리 화면이 초기 핵심 범위에 들어온다.
- 로그·오류에서 인증값을 가리는 규칙을 시험으로 지켜야 한다(AC-20).

다시 검토할 시점:

- 사내 LDAP/AD 또는 OIDC 연동 환경이 확인될 때(선택지 B 추가).
- 기밀 프로젝트 열람 제한이 필요해질 때(프로젝트 멤버십).
- Jira 인증 주체가 결정될 때(PRD §13-6).

| 프로젝트 간 열람 제한(기밀 프로젝트)이 필요한가 | 프로젝트 담당자, 이해관계자 |
| 사내 LDAP/AD, SSO, 망 내 OIDC 제공 여부와 연동 승인 절차 | 사내 인증·보안 담당 |
| 사내 계정·비밀번호 정책(복잡도, 만료, 잠금) 중 Tevro에 적용할 기준 | 사내 보안 담당 |
| 에이전트 전용 계정을 허용하는 사내 정책이 있는지 | 사내 보안 담당 |
| 토큰 만료 기본값·최대값과 세션 만료 시간 | 프로젝트 담당자, 사내 보안 담당 |
| 템플릿 삭제·프로젝트 삭제를 편집자에게 허용할지 | 프로젝트 담당자 |
| HTTPS 종단 위치(세션 쿠키 Secure 전제) | 사내 인프라 담당(ADR-0002) |

## 후속 작업

- [ ] 기밀 프로젝트 열람 제한 필요 여부를 이해관계자에게 확인한다.
- [ ] 사용자·인증 수단·세션·토큰 테이블 초안을 만든다.
- [ ] 최초 관리자 생성 관리 명령을 설계한다.
- [ ] 토큰 발급·폐기 화면과 API를 설계한다(ADR-0006).
- [ ] 로그·오류의 인증값 가림 규칙과 AC-20 시험을 만든다.
- [ ] 채택하면 PRD §13-3과 N-06 비고를 갱신한다.
