## 배경

식별자는 첫 테이블과 첫 CLI 명령의 계약이다. 에이전트 스크립트는 ID를 저장해 두므로 나중에 형식을 바꾸면 F-C04('GUI에 표시된 공정과 CLI 명령이 같은 식별자를 사용') 계약이 깨진다. PRD §13-12가 이 결정을 구현 전 결정 사항으로 둔다.

문서의 요구는 다음과 같다.

| 요구 | 근거 |
| --- | --- |
| 공정의 ID는 제목을 바꿔도 유지한다 | §7.2, AC-05 |
| 템플릿의 공정 식별자와 프로젝트 실행본의 공정 식별자를 구분한다 | §7.2 |
| 템플릿을 적용하면 새 공정에 새 식별자를 부여한다 | F-T05 |
| 제목 또는 식별자로 공정을 찾는다 | F-P07 |
| 기존 Jira 이슈의 키 또는 URL로 연결한다 | F-J02 |

삭제 방식도 같은 계약에 묶인다. 물리 삭제인지 삭제 표시(tombstone)인지에 따라 다음이 달라진다.

- 삭제된 ID를 다시 쓸 수 있는지.
- 없는 ID를 조회했을 때의 오류가 일관적인지(F-C05).
- Jira 단계에서 매핑과 'Tevro가 관리하는 링크' 구분을 보존할 수 있는지(F-P06, §6.7 '링크 의미와 재시도'의 'Tevro에서 연결을 제거했다고 Jira의 해당 링크를 자동 삭제하지 않는다' 항목).

PRD §6.1 표 아래 문단은 두 가지 미결 사항을 더 적는다. 하나는 A → B → C에서 B를 삭제하면 A와 C 사이의 순서 정보가 사라진다는 점이고(§13-15), 다른 하나는 프로젝트 삭제·보관이 정의되지 않았다는 점이다(§13-14). CLI 단건 삭제(`task delete`)는 F-C07 확인 대상에 명시되어 있지 않다.

PRD §6.9 공정 계층은 두 가지를 더한다. 하위가 있는 공정을 삭제할 때 하위까지 지울지 한 단계 올릴지(§13-15에 합쳐진 쟁점)와, 템플릿이 포함관계(`parent_id`)도 복제해야 한다는 점(F-H10, AC-30)이다. 식별자 체계 자체는 바꾸지 않는다.

## 제안하는 결정

### 1. 식별자: 타입 접두사 + ULID(또는 UUIDv7)

| 대상 | 접두사 | 비고 |
| --- | --- | --- |
| 프로젝트 | `prj_` | |
| 공정(프로젝트 실행본) | `tsk_` | |
| 종속성 | `dep_` | API는 (선행, 후속) 공정 쌍으로도 지정할 수 있다(ADR-0006) |
| 템플릿 | `tpl_` | 재사용 단계 |
| 템플릿 공정 | `ttk_` | 재사용 단계. `tsk_`와 섞이지 않는다 |
| 사용자 | `usr_` | ADR-0004 |
| 개인 액세스 토큰의 식별자 | `tok_` | 비밀값이 아니다(ADR-0004) |
| 변경 묶음 안의 임시 ID | `tmp_` | 한 요청 안에서만 유효하다(ADR-0006) |

형식 예시는 `tsk_01k6z3x8m4q2w9e7r5t1y0v3pa`다(접두사 + ULID 26자). 실제 값이 아니다.

- 전역에서 유일한 불투명 ID다. 프로젝트 ID 없이도 공정을 가리킬 수 있다.
- 서버는 경로·본문의 접두사를 검사한다. 템플릿 공정 ID(`ttk_`)를 프로젝트 공정 자리에 넣으면 형식 오류로 바로 거부한다(§7.2).
- 템플릿을 적용하면 `ttk_`마다 새 `tsk_`를 발급한다(F-T05). 실행본에 원본 템플릿 공정 ID를 저장할지는 초기 범위에서 다루지 않는다. 템플릿 변경을 기존 프로젝트에 병합하는 기능이 범위 밖이기 때문이다(§6.6 복제 규칙).
- Jira 이슈 키(예: `ABC-123`, '영문 프로젝트 키-숫자' 꼴)와 헷갈리지 않는다. F-J02가 Jira 키를 입력으로 받으므로 두 형식이 겹치면 안 된다.
- GUI 상세 패널에 같은 ID를 복사 버튼과 함께 표시한다(F-C04).
- 삭제된 ID는 다시 쓰지 않는다. 시간과 무작위 값으로 만드는 ID라 재사용이 생기지 않는다.
- 표기 대소문자는 구현할 때 하나로 고정하고, 입력은 대소문자를 구분하지 않는다. ULID 명세는 대소문자를 구분하지 않는다. [ULID 명세][ulid]
- 공정 계층(PRD §6.9)은 접두사를 늘리지 않는다. 하위 공정도 `tsk_`, 템플릿의 하위 공정도 `ttk_`다. 상위 공정 ID(`parent_id`)는 같은 프로젝트의 `tsk_` ID를 가리킨다(ADR-0003 1.7).
- 템플릿을 적용하면 `parent_id`도 새로 발급한 `tsk_`로 바꿔 복제한다. 종속성을 새 공정끼리 다시 잇는 것(F-T05)과 같은 방식이다(F-H10, AC-30). 프로젝트에서 템플릿을 추출(F-T02)할 때도 포함관계를 그대로 저장한다.

ULID와 UUIDv7 중 하나를 고른다. ULID를 제안하지만 결정 필요다.

| 기준 | ULID | UUIDv7 |
| --- | --- | --- |
| 표준 | 커뮤니티 명세 [ULID 명세][ulid] | IETF RFC 9562(2024-05) [RFC 9562][rfc9562] |
| 문자열 길이 | 26자, Crockford base32 | 36자, 하이픈 포함 16진수 |
| 정렬 | 생성 시각순으로 정렬 가능(밀리초 Unix 시간 48비트) | 생성 시각순으로 정렬 가능(밀리초 Unix 시간) |
| CLI 입력 편의 | 짧다 | 길다 |
| 저장 | 문자열 | 문자열 또는 PostgreSQL `uuid` 형식 |

두 방식 모두 생성 시각이 ID에 드러난다. 사내 도구라 문제가 없다고 보지만 이해관계자 확인 대상에 넣는다.

### 2. 삭제: 초기 핵심은 영향 미리 보기 + 명시적 확인 후 물리 삭제

**공정 삭제**

- 삭제 전에 영향을 보여 준다. GUI는 확인 대화상자에, CLI는 dry-run 또는 `--yes` 없는 실행 결과에 보여 준다([ADR-0007](./0007-cli-contract.md)).
- 영향은 다음 네 가지다.
  - 함께 사라지는 연결(선행·후속).
  - 끊기는 선후 경로(PRD §13-15).
  - 하위가 있으면 함께 사라지거나 한 단계 올라가는 하위 공정 수와 하위의 연결 수(아래 '하위가 있는 공정의 삭제').
  - 영향받는 Jira 매핑(Jira 단계, AC-21).
- 확인 후 공정 행을 물리 삭제하고 연결은 외래 키 CASCADE로 함께 지운다([ADR-0003](./0003-storage-and-concurrency.md)).
- 실제 Jira 이슈는 지우지 않는다(F-P06).

**끊기는 선후 경로의 정의와 재연결 — 제안, 결정 필요(PRD §13-15)**

- 정의: 삭제할 공정 B의 직접 선행 p와 직접 후속 s의 쌍 가운데, B를 지운 뒤 p에서 s로 가는 경로가 남지 않는 쌍.
- 예: A → B → C만 있으면 (A, C)가 끊긴다. A → C가 따로 있거나 A → X → C 경로가 있으면 끊기지 않는다.
- 자동으로 연결을 만들지 않는다. 사용자가 고른 쌍만 같은 변경 묶음 안에서 `dependency.add`로 함께 적용하는 방식을 제안한다(ADR-0006). CLI는 끊기는 쌍을 모두 다시 잇는 선택 옵션(예: `task delete <id> --reconnect`)을 둔다.
- 재연결한 p → s는 순환을 만들지 않는다. 삭제 전에 p → B → s 경로가 있었으므로, s에서 p로 가는 경로가 있었다면 이미 순환이었을 것이기 때문이다. 이미 있는 연결은 건너뛴다.

**하위가 있는 공정의 삭제 — 제안, 결정 필요(PRD §13-15)**

| 선택지 | 내용 | 평가 |
| --- | --- | --- |
| (A) 영향 미리 보기 후 하위까지 삭제 — 제안 | 자손 공정 전체와 그 연결을 함께 지운다. `parent_id` 외래 키의 `ON DELETE CASCADE`로 구현한다(ADR-0003 1.7). 미리 보기에 자손 수, 자손의 연결 수, Jira 단계에서는 자손의 매핑 수를 넣는다 | 단순하고 DB가 일관성을 지킨다. 실수하면 손실 범위가 크므로 GUI 확인 대화상자와 CLI `--yes`를 반드시 거친다 |
| (B) 하위를 한 단계 올림 | 하위의 `parent_id`를 삭제할 공정의 상위로 바꾼 뒤 공정만 지운다. 하위끼리의 연결은 형제 관계가 유지되므로 남는다. 삭제할 공정이 맺었던 연결은 사라지고 끊기는 선후 경로로 표시한다 | 데이터를 잃지 않는다. 대신 하위가 윗 층으로 올라가 의도하지 않은 구조가 되고, 서버가 같은 트랜잭션에서 하위를 먼저 옮겨야 한다 |

(A)를 기본으로 제안한다. (B)가 필요하다고 확인되면 CLI 옵션(예: `task delete <id> --promote-children`)과 GUI 선택지로 더하는 방식을 제안한다. 어느 쪽이든 끊기는 선후 경로는 삭제할 공정의 층에서 계산한다. 자손 수와 자손의 연결 수는 변경 묶음 dry-run의 영향 정보에 담는다(ADR-0006 §4).

**삭제된 ID의 오류**

- 작업 대상이 없거나 삭제되었으면 `NOT_FOUND`다. 작업 대상은 경로로 지정한 대상과, 변경 묶음의 `task.update`·`task.delete`·`task.move`가 가리키는 공정이다. 단건 API로 오든 변경 묶음으로 오든 같다.
- 다른 공정을 참조하는 작업(`dependency.add`·`dependency.remove`의 선행·후속 공정, `task.create`·`task.move`의 `parentId`)에서 참조한 공정이 없으면 `REFERENCE_NOT_FOUND`다(ADR-0006). 계층 전용 '상위 없음' 코드는 두지 않는다.
- '존재한 적 없음'과 '삭제됨'을 구분하지 않는다. 일관된 결과를 위해서다.

**복구 수단**

- 변경 이력은 후속 검토 대상(F-M08)이므로 잘못 삭제한 공정을 되살리는 수단은 백업뿐이다(N-04, PRD §6.1).
- 휴지통(소프트 삭제)은 후속 검토로 둔다.

**Jira 단계에서 재검토할 것**

- 공정을 물리 삭제하면서 Jira 매핑과 반영 결과(특히 '결과 미확인' 생성 건)까지 지우면, Jira에 고아 이슈가 생겨도 찾을 단서가 사라진다.
- Jira 단계에 들어가기 전에 삭제 표시(tombstone)로 바꿀지, 매핑·반영 결과만 따로 보존할지 다시 검토한다.
- 삭제 표시를 도입해도 API는 `NOT_FOUND`를 유지하는 것을 제안한다. 클라이언트 계약을 바꾸지 않기 위해서다.
- 종속성에 `dep_` ID를 두면 반영 결과를 관계 ID에 묶을 수 있다. 방향을 바꾸면 삭제 + 추가가 되어 새 `dep_`가 생기므로, 옛 반영 결과가 '반영 후 변경됨'임을 알아내기 쉽다(PRD §6.7 검토 제안과 연계).

### 3. 프로젝트 삭제·보관 — 제안, 결정 필요(PRD §13-14)

| 항목 | 제안 |
| --- | --- |
| 기본 동작 | 보관(archive). 보관한 프로젝트는 기본 목록에서 숨기고 읽기 전용으로 둔다. 보관 해제를 허용한다 |
| 물리 삭제 | 관리자 권한(ADR-0004), 영향 확인(공정·연결 수, Jira 단계에서는 매핑 수), 명시적 확인(`--yes`)을 거친다. 공정·연결은 CASCADE로 지운다 |
| CLI 동등성 | 보관·보관 해제·삭제 모두 CLI 대상에 포함한다(F-C01) |
| 초기 핵심 포함 여부 | 결정 필요 |

### 4. 템플릿 삭제와 출처 — 재사용 단계(F-T09, F-T10, AC-22)

- 프로젝트에는 출처를 템플릿 ID, 템플릿 이름, 적용 당시 정의를 식별할 정보(리비전)로 복사해 저장한다. 템플릿 테이블에 대한 외래 키로 묶지 않는다.
- 그래서 템플릿을 삭제해도 프로젝트는 남고 출처를 계속 표시할 수 있다(AC-22). 그 `tpl_` ID를 조회하면 `NOT_FOUND`다.
- 리비전 형식과 수정 이력 보존 방식은 PRD §13-9에서 정한다.
- 템플릿 공정도 포함관계를 가진다. 템플릿 공정의 상위 ID는 같은 템플릿의 `ttk_` ID다. 적용·추출 시 복제 규칙은 §1을 따른다(F-H10).

## 검토한 선택지

### 선택지 A: 타입 접두사 + 전역 불투명 ID만 사용

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 낮음. ID 생성 함수 하나와 접두사 검사 |
| 폐쇄망 반입·운영 부담 | 없음. 작은 생성 함수로 충분하고 외부 서비스가 필요 없다 |
| GUI·CLI 동등성(원칙 7) | GUI와 CLI가 같은 문자열을 쓴다(F-C04) |
| 관련 요구사항 적합성 | §7.2(템플릿·실행본 구분), F-T05(새 ID), AC-05(제목 변경 후 유지)를 충족한다. Jira 키와 겹치지 않는다(F-J02) |
| 팀 숙련도 | 확인 필요. 일반적인 방식이라 부담은 작다고 본다 |

장점: 단순하다. 형식만 보고 대상 종류를 알 수 있다. 재사용이 생기지 않는다.

단점: 사람이 손으로 입력하기에는 길다. CLI에서는 복사해 붙이거나 이전 명령의 JSON 출력에서 꺼내 써야 한다.

### 선택지 B: A + 프로젝트 안 순번 표시키(보조 식별자)

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간. 프로젝트별 순번 발급(동시성 포함), 표시키 → ID 해석 계층이 필요하다 |
| 폐쇄망 반입·운영 부담 | 없음 |
| GUI·CLI 동등성(원칙 7) | 두 가지 식별자를 모두 받아야 하므로 입력 규칙이 복잡해진다. 출력과 저장은 정식 ID로 통일해야 한다 |
| 관련 요구사항 적합성 | F-P07 사람 검색에 편하다. 다만 템플릿 적용 시 순번을 새로 매겨야 하고(F-T05), 삭제로 생긴 빈 번호를 다시 쓰면 안 된다 |
| 팀 숙련도 | 확인 필요 |

장점: 사람이 화면에서 보고 CLI에 입력하기 쉽다(예: 12번 공정).

단점:

- `#12` 같은 표기는 셸에서 `#` 뒤가 주석으로 처리될 수 있어 따옴표가 필요하다.
- `T-12` 같은 '영문-숫자' 표기는 Jira 이슈 키 꼴과 겹친다.
- 표시키는 프로젝트 안에서만 유일하므로 항상 프로젝트를 함께 지정해야 한다.

초기에는 선택지 A만 제공하고, B는 사용자 피드백을 받은 뒤 추가 검토하는 것을 제안한다. 나중에 B를 더해도 A의 계약은 깨지지 않는다.

### 삭제 방식 비교

| 기준 | 물리 삭제 + CASCADE(초기 제안) | 삭제 표시(tombstone) |
| --- | --- | --- |
| 복잡도 | 낮음 | 중간. 모든 조회에 삭제 제외 조건이 필요하다 |
| 일관성(§7.2) | 외래 키가 보장한다 | 애플리케이션 규칙으로 보장해야 한다 |
| 복구 | 백업뿐 | 되살리기 기능을 만들 수 있다 |
| Jira 매핑 보존 | 함께 사라진다 | 보존할 수 있다 |
| 하위가 있는 공정 | 자손도 CASCADE로 지운다(선택지 A) | 자손에도 삭제 표시가 필요하다 |
| 적합한 시점 | 초기 핵심(Jira 없음) | Jira 단계 진입 전 재검토 |

## 트레이드오프

- 전역 불투명 ID는 견고하지만 사람이 읽고 입력하기 어렵다. GUI 복사 버튼과 CLI JSON 출력으로 보완한다.
- 물리 삭제는 단순하고 일관성을 DB가 지키지만, 되살리기는 백업으로만 가능하다.
- 재연결을 자동으로 하지 않으면 사용자가 매번 고르는 부담이 있다. 대신 의도하지 않은 연결이 생기지 않는다.
- 프로젝트 보관을 기본으로 하면 데이터가 계속 쌓인다. 물리 삭제 절차를 함께 둔다.
- 하위까지 삭제하면 구현이 단순한 대신 한 번의 실수로 자손 전체를 잃는다. 미리 보기에 자손 수를 넣고 명시적 확인을 요구해 보완한다.

## 결과

쉬워지는 것:

- 첫 테이블 스키마와 첫 CLI 명령의 식별자 계약을 확정할 수 있다.
- 템플릿 공정 ID 오용을 형식 검사로 바로 거부할 수 있다.
- 삭제 영향 미리 보기를 변경 묶음 dry-run으로 구현할 수 있다(ADR-0006). 하위가 있는 공정의 미리 보기도 같은 영향 정보로 구현한다.
- 템플릿 복제가 종속성과 포함관계를 같은 ID 매핑으로 다시 잇는다(AC-30).

어려워지는 것:

- 사람이 CLI에 ID를 직접 입력하기 불편하다.
- Jira 단계 진입 전에 삭제 방식을 다시 검토해야 한다.

다시 검토할 시점:

- Jira 선택 연동 단계에 들어가기 전(삭제 표시 여부).
- 사용자들이 CLI 입력 불편을 반복해서 제기할 때(선택지 B).
- 프로젝트 수가 늘어 보관·삭제 정책이 운영 문제가 될 때.

## 채택 전 확인할 사항

| 항목 | 확인 대상 |
| --- | --- |
| ULID와 UUIDv7 중 사내 표준이나 선호가 있는지 | 사내 아키텍처 담당 |
| ID에 생성 시각이 드러나는 것이 문제가 되는지 | 사내 보안 담당 |
| 공정 삭제 시 재연결 제안을 원하는지(PRD §13-15) | 프로젝트 담당자, 표준 공정 관리 담당자 |
| 프로젝트 보관·삭제를 초기 핵심에 넣을지(PRD §13-14) | 프로젝트 담당자 |
| 연결이 있는 공정을 CLI로 삭제할 때 `--yes`를 항상 요구할지 | 프로젝트 담당자, 에이전트 사용 담당 |
| 하위가 있는 공정을 삭제할 때 하위까지 지울지(A), 한 단계 올릴지(B)(PRD §13-15) | 프로젝트 담당자, 표준 공정 관리 담당자 |
