## 배경

식별자는 첫 테이블과 첫 CLI 명령의 계약이다. 에이전트 스크립트는 ID를 저장해 두므로 나중에 형식을 바꾸면 F-C04('GUI에 표시된 공정과 CLI 명령이 같은 식별자를 사용') 계약이 깨진다. 이 ADR 작성 당시(2026-10-07) PRD §13-12는 이 결정을 구현 전 결정 사항으로 두었다. 현재 §13-12는 이 ADR의 결정을 반영했다.

문서의 요구는 다음과 같다.

| 요구 | 근거 |
| --- | --- |
| 공정의 ID는 제목을 바꿔도 유지한다 | §7.2, AC-05 |
| 템플릿의 공정 식별자와 프로젝트 실행본의 공정 식별자를 구분한다 | §7.2 |
| 템플릿을 적용하면 새 공정에 새 식별자를 부여한다 | F-T05 |
| 제목 또는 식별자로 공정을 찾는다 | F-P07 |
| 기존 Jira 이슈의 키 또는 URL로 연결한다 | F-J02 |

삭제 방식도 같은 계약에 묶인다. 물리 삭제인지 삭제 표시(tombstone)인지에 따라 다음이 달라진다.

- 삭제된 ID를 다시 쓸 수 있는지.
- 없는 ID를 조회했을 때의 오류가 일관적인지(F-C05).
- Jira 단계에서 매핑과 'Tevro가 관리하는 링크' 구분을 보존할 수 있는지(F-P06, §6.7 '링크 의미와 재시도'의 'Tevro에서 연결을 제거했다고 Jira의 해당 링크를 자동 삭제하지 않는다' 항목).

이 ADR 작성 당시 PRD §6.1 표 아래 문단은 두 가지 미결 사항을 더 적었다. 하나는 A → B → C에서 B를 삭제하면 A와 C 사이의 순서 정보가 사라진다는 점이고(§13-15), 다른 하나는 프로젝트 삭제·보관이 정의되지 않았다는 점이다(§13-14). CLI 단건 삭제(`task delete`)도 F-C07 확인 대상에 명시되어 있지 않았다. 2026-10-08 이 ADR이 채택되어 세 가지가 정해졌다(아래 '결정'). CLI 단건 삭제의 `--yes` 규칙은 [ADR-0007](./0007-cli-contract.md)과 함께 정해졌다. 현재 PRD §13-14·§13-15는 이 결정을 반영했다.

PRD §6.9 공정 계층은 두 가지를 더한다. 하위가 있는 공정을 삭제할 때 하위까지 지울지 한 단계 올릴지(§13-15에 합쳐진 쟁점)와, 템플릿이 포함관계(`parent_id`)도 복제해야 한다는 점(F-H10, AC-30)이다. 식별자 체계 자체는 바꾸지 않는다. 앞의 쟁점은 2026-10-08 하위까지 삭제로 정해졌다.

## 결정

2026-10-08 결정권자가 식별자로 선택지 A(타입 접두사 + 전역 불투명 ID)를 채택하고, 불투명 ID 형식은 ULID로 정했다. 삭제는 영향 미리 보기와 명시적 확인 후 물리 삭제로, 하위가 있는 공정은 하위까지 삭제하는 (A)로 정했다.

| 항목 | 결정 |
| --- | --- |
| 1. 식별자 형식 | 선택지 A: 타입 접두사 + ULID. UUIDv7은 채택하지 않는다. 프로젝트 안 순번 표시키(선택지 B)는 처음부터 두지 않는다. 나중에 추가 검토할 수 있다 |
| 2. 공통 삭제 방식 | 영향 미리 보기 → 명시적 확인 → 물리 삭제. 연결은 외래 키 CASCADE로 함께 지운다. 삭제 표시(tombstone)는 Jira 단계 진입 전에 재검토한다 |
| 3. 하위가 있는 공정의 삭제 | (A) 영향 미리 보기 후 하위까지 삭제. 하위를 한 단계 올리는 옵션은 두지 않는다 |
| 4. 끊기는 선후 경로 | 자동 재연결 없음. 삭제 미리 보기에 끊기는 쌍을 보여 주고, 사용자가 고른 쌍만 같은 변경 묶음에서 잇는다. CLI는 끊기는 쌍을 모두 잇는 `--reconnect` 옵션을 둔다 |
| 5. 프로젝트 삭제·보관 | 관리자 삭제(영향 확인 + 명시적 확인)는 초기 핵심에 넣는다. 보관(숨김·읽기 전용)은 다음 단계에서 제공한다. 권한은 관리자만이며 ADR-0004 채택으로 이미 정해졌다 |

결정권자가 명시적으로 답한 범위는 1, 3, 4, 5다. 2는 결정권자에게 보인 질문 문구에 들어 있었고, 그 답으로 함께 정해진 것으로 기록한다. 3에서 결정권자에게는 '기본은 하위까지 삭제 + 한 단계 올리는 옵션(`--promote-children`)'도 함께 보였으나 결정권자는 이것을 고르지 않았다. 그래서 하위를 올리는 옵션은 CLI와 GUI 어디에도 두지 않는다. 선택 사유는 따로 기록되지 않았다. 제안 단계의 판단은 각 절의 '제안 단계 원문(기록)'과 '검토한 선택지'에 그대로 둔다.

§1의 접두사 표와 세부 규칙(접두사 검사, 템플릿 적용 시 새 ID 발급, 삭제된 ID 비재사용, `parent_id` 복제 등)과 §2의 삭제된 ID 오류·복구 수단에는 결정권자가 따로 답하지 않았다. 선택지 A와 공통 삭제 방식을 이루는 세부로 보고 제안 그대로 기록한다.

제안과 달라진 점은 프로젝트 삭제·보관의 제공 순서다. 제안 단계에서는 보관을 기본 동작으로 두고 물리 삭제를 관리자 절차로 함께 두는 것을 제안했고, 초기 핵심 포함 여부는 결정 필요로 두었다(§3 '제안 단계 원문'). 결정은 관리자 삭제만 초기 핵심에 넣고 보관은 다음 단계로 미룬다. 사유는 기록되지 않았다. 하위를 한 단계 올리는 (B)는 제안 단계에서도 기본이 아니었으나 '필요하다고 확인되면 옵션으로 더한다'고 적었다. 이번 결정으로 그 옵션은 두지 않는다. 나머지(ULID, 순번 표시키를 처음에 두지 않음, 물리 삭제, 자동 재연결 없음과 `--reconnect`, 하위까지 삭제)는 제안과 같다.

이번 결정에서 정하지 않은 것은 다음과 같다. 모두 '남은 확인 사항'에 둔다.

- ID에 생성 시각이 드러나는 것이 문제가 되는지에 대한 사내 보안 확인.
- ULID 표기의 대소문자. 구현할 때 하나로 고정한다.
- 삭제 표시(tombstone) 도입 여부. Jira 단계 진입 전에 재검토한다.
- 휴지통(소프트 삭제). 후속 검토로 둔다.
- 프로젝트 보관 해제 권한.

템플릿 삭제와 출처(§4)는 재사용 단계의 범위라 이번 결정에서 다루지 않았다. 템플릿 삭제 권한(관리자만)은 ADR-0004에서 정했다.

### 1. 식별자: 타입 접두사 + ULID — 채택

| 대상 | 접두사 | 비고 |
| --- | --- | --- |
| 프로젝트 | `prj_` | |
| 공정(프로젝트 실행본) | `tsk_` | |
| 종속성 | `dep_` | API는 (선행, 후속) 공정 쌍으로도 지정할 수 있다(ADR-0006) |
| 템플릿 | `tpl_` | 재사용 단계 |
| 템플릿 공정 | `ttk_` | 재사용 단계. `tsk_`와 섞이지 않는다 |
| 사용자 | `usr_` | ADR-0004 |
| 개인 액세스 토큰의 식별자 | `tok_` | 비밀값이 아니다(ADR-0004) |
| 변경 묶음 안의 임시 ID | `tmp_` | 한 요청 안에서만 유효하다(ADR-0006) |

형식 예시는 `tsk_01k6z3x8m4q2w9e7r5t1y0v3pa`다(접두사 + ULID 26자). 실제 값이 아니다.

- 전역에서 유일한 불투명 ID다. 프로젝트 ID 없이도 공정을 가리킬 수 있다.
- 서버는 경로·본문의 접두사를 검사한다. 템플릿 공정 ID(`ttk_`)를 프로젝트 공정 자리에 넣으면 형식 오류로 바로 거부한다(§7.2).
- 템플릿을 적용하면 `ttk_`마다 새 `tsk_`를 발급한다(F-T05). 실행본에 원본 템플릿 공정 ID를 저장할지는 초기 범위에서 다루지 않는다. 템플릿 변경을 기존 프로젝트에 병합하는 기능이 범위 밖이기 때문이다(§6.6 복제 규칙).
- Jira 이슈 키(예: `ABC-123`, '영문 프로젝트 키-숫자' 꼴)와 헷갈리지 않는다. F-J02가 Jira 키를 입력으로 받으므로 두 형식이 겹치면 안 된다.
- GUI 상세 패널에 같은 ID를 복사 버튼과 함께 표시한다(F-C04).
- 삭제된 ID는 다시 쓰지 않는다. 시간과 무작위 값으로 만드는 ID라 재사용이 생기지 않는다.
- 표기 대소문자는 구현할 때 하나로 고정하고, 입력은 대소문자를 구분하지 않는다. ULID 명세는 대소문자를 구분하지 않는다. [ULID 명세][ulid]
- 공정 계층(PRD §6.9)은 접두사를 늘리지 않는다. 하위 공정도 `tsk_`, 템플릿의 하위 공정도 `ttk_`다. 상위 공정 ID(`parent_id`)는 같은 프로젝트의 `tsk_` ID를 가리킨다(ADR-0003 1.7).
- 템플릿을 적용하면 `parent_id`도 새로 발급한 `tsk_`로 바꿔 복제한다. 종속성을 새 공정끼리 다시 잇는 것(F-T05)과 같은 방식이다(F-H10, AC-30). 프로젝트에서 템플릿을 추출(F-T02)할 때도 포함관계를 그대로 저장한다.

2026-10-08 결정권자가 ULID를 채택했다. UUIDv7은 채택하지 않았다. 선택 사유는 따로 기록되지 않았다. 아래 표는 제안 단계에서 두 방식을 비교한 기록이다.

제안 단계 원문(기록): 'ULID와 UUIDv7 중 하나를 고른다. ULID를 제안하지만 결정 필요다.'

| 기준 | ULID — 채택 | UUIDv7 — 채택하지 않음 |
| --- | --- | --- |
| 표준 | 커뮤니티 명세 [ULID 명세][ulid] | IETF RFC 9562(2024-05) [RFC 9562][rfc9562] |
| 문자열 길이 | 26자, Crockford base32 | 36자, 하이픈 포함 16진수 |
| 정렬 | 생성 시각순으로 정렬 가능(밀리초 Unix 시간 48비트) | 생성 시각순으로 정렬 가능(밀리초 Unix 시간) |
| CLI 입력 편의 | 짧다 | 길다 |
| 저장 | 문자열 | 문자열. 2026-10-07 작성 때 적은 PostgreSQL `uuid` 형식은 저장소가 SQLite로 정해져(ADR-0003 채택) 해당하지 않는다 |

두 방식 모두 생성 시각이 ID에 드러난다. 채택한 ULID도 마찬가지다. 사내 도구라 문제가 없다고 보지만(작성자 판단), 사내 보안 담당의 확인은 '남은 확인 사항'이다.

### 2. 삭제: 초기 핵심은 영향 미리 보기 + 명시적 확인 후 물리 삭제 — 채택

**공정 삭제**

- 삭제 전에 영향을 보여 준다. GUI는 확인 대화상자에, CLI는 dry-run 또는 `--yes` 없는 실행 결과에 보여 준다([ADR-0007](./0007-cli-contract.md)).
- 영향은 다음 네 가지다.
  - 함께 사라지는 연결(선행·후속).
  - 끊기는 선후 경로(PRD §13-15).
  - 하위가 있으면 함께 사라지는 자손 공정과 자손의 연결(아래 '하위가 있는 공정의 삭제').
  - 영향받는 Jira 매핑(Jira 단계, AC-21).
- 서버는 영향을 변경 묶음 dry-run 응답의 `impact`에 담는다([ADR-0006](./0006-server-api-contract.md) §4). 함께 사라지는 연결은 `removedDependencies`(자손의 연결 포함), 끊기는 선후 경로는 `brokenPaths`, 함께 사라지는 자손 공정은 `removedTasks`다. Jira 매핑 영향은 Jira 단계에서 더한다. 하위를 올리는 옵션이 없으므로 올림 관련 필드는 두지 않는다.
- 확인 후 공정 행을 물리 삭제하고 연결은 외래 키 CASCADE로 함께 지운다([ADR-0003](./0003-storage-and-concurrency.md)).
- CLI `task delete`는 연결 유무와 관계없이 `--yes`가 있어야 실행한다. `--yes`가 없으면 아무것도 바꾸지 않고, 서버 dry-run으로 얻은 미리 보기를 보여 준 뒤 종료 코드 2로 끝낸다. 연결 하나만 지우는 `dependency remove`는 `--yes` 없이 실행한다([ADR-0007](./0007-cli-contract.md), 2026-10-08 채택).
- 실제 Jira 이슈는 지우지 않는다(F-P06).

**끊기는 선후 경로의 정의와 재연결 — 결정(2026-10-08, PRD §13-15)**

- 정의: 삭제할 공정 B의 직접 선행 p와 직접 후속 s의 쌍 가운데, B를 지운 뒤 p에서 s로 가는 경로가 남지 않는 쌍.
- 예: A → B → C만 있으면 (A, C)가 끊긴다. A → C가 따로 있거나 A → X → C 경로가 있으면 끊기지 않는다.
- 자동으로 연결을 만들지 않는다. 삭제 미리 보기에 끊기는 쌍(`brokenPaths`)을 보여 주고, 사용자가 고른 쌍만 같은 변경 묶음 안에서 `dependency.add`로 함께 적용한다(ADR-0006).
- CLI는 끊기는 쌍을 모두 다시 잇는 `task delete <id> --reconnect` 옵션을 둔다(ADR-0007). 일부 쌍만 이으려면 `graph apply --file`에 `task.delete`와 고른 쌍의 `dependency.add`를 함께 담는다.
- 이 묶음은 같은 대상을 겹쳐 다루지 않는다. `task.delete`의 대상은 B이고, 추가하는 연결 p → s는 B를 참조하지 않는다. p와 s는 B의 형제이므로(선행관계는 같은 상위 안에서만 맺는다, PRD §6.9 R3) 함께 지워지는 자손도 아니다. 그래서 같은 대상을 한 묶음에서 겹쳐 다루는 애매한 조합을 `VALIDATION_INPUT`으로 거부하는 규칙(ADR-0006)에 걸리지 않는다.
- 재연결한 p → s는 순환을 만들지 않는다. 삭제 전에 p → B → s 경로가 있었으므로, s에서 p로 가는 경로가 있었다면 이미 순환이었을 것이기 때문이다. 끊기는 쌍은 정의상 B를 지운 뒤 p에서 s로 가는 경로가 없으므로 p → s 연결도 없다. 다시 이어도 중복 연결이 생기지 않는다.

제안 단계에서는 '제안, 결정 필요'로 두었다. 결정은 제안과 같다. 제안 단계 원문(기록): '자동으로 연결을 만들지 않는다. 사용자가 고른 쌍만 같은 변경 묶음 안에서 `dependency.add`로 함께 적용하는 방식을 제안한다(ADR-0006). CLI는 끊기는 쌍을 모두 다시 잇는 선택 옵션(예: `task delete <id> --reconnect`)을 둔다.' 같은 원문의 '이미 있는 연결은 건너뛴다'는 위 정의상 해당하는 경우가 없어 중복 연결이 생기지 않는다는 문장으로 바꿨다.

**하위가 있는 공정의 삭제 — 결정(2026-10-08): (A) 하위까지 삭제(PRD §13-15)**

| 선택지 | 내용 | 평가 |
| --- | --- | --- |
| (A) 영향 미리 보기 후 하위까지 삭제 — 채택 | 자손 공정 전체와 그 연결을 함께 지운다. `parent_id` 외래 키의 `ON DELETE CASCADE`로 구현한다(ADR-0003 1.7). 미리 보기에 자손 수, 자손의 연결 수, Jira 단계에서는 자손의 매핑 수를 넣는다 | 단순하고 DB가 일관성을 지킨다. 실수하면 손실 범위가 크므로 GUI 확인 대화상자와 CLI `--yes`를 반드시 거친다 |
| (B) 하위를 한 단계 올림 — 채택하지 않음 | 하위의 `parent_id`를 삭제할 공정의 상위로 바꾼 뒤 공정만 지운다. 하위끼리의 연결은 형제 관계가 유지되므로 남는다. 삭제할 공정이 맺었던 연결은 사라지고 끊기는 선후 경로로 표시한다 | 데이터를 잃지 않는다. 대신 하위가 윗 층으로 올라가 의도하지 않은 구조가 되고, 서버가 같은 트랜잭션에서 하위를 먼저 옮겨야 한다 |

2026-10-08 결정권자가 (A)를 채택했다. 결정권자에게는 '기본은 하위까지 삭제 + 한 단계 올리는 옵션(`--promote-children`)'도 함께 보였으나 고르지 않았다. 그래서 하위를 한 단계 올리는 옵션은 CLI와 GUI 어디에도 두지 않는다. 선택 사유는 따로 기록되지 않았다.

제안 단계 원문(기록, 올림 옵션은 채택하지 않음): '(A)를 기본으로 제안한다. (B)가 필요하다고 확인되면 CLI 옵션(예: `task delete <id> --promote-children`)과 GUI 선택지로 더하는 방식을 제안한다.'

끊기는 선후 경로는 삭제할 공정의 층에서 계산한다. 자손의 연결은 자손끼리만 맺어지므로(PRD §6.9 R3) 모두 함께 지워지고, 남는 공정 사이에 끊기는 경로를 만들지 않는다. 함께 사라지는 자손 공정은 영향 정보의 `removedTasks`에, 자손의 연결은 `removedDependencies`에 담는다(ADR-0006 §4). 미리 보기의 자손 수와 자손의 연결 수는 이 목록에서 센다.

**삭제된 ID의 오류**

- 작업 대상이 없거나 삭제되었으면 `NOT_FOUND`다(HTTP 404, CLI 종료 코드 6). 작업 대상은 경로로 지정한 대상과, 변경 묶음의 `task.update`·`task.delete`·`task.move`가 가리키는 공정이다. 단건 API로 오든 변경 묶음으로 오든 같다.
- 다른 공정을 참조하는 작업(`dependency.add`·`dependency.remove`의 선행·후속 공정, `task.create`·`task.move`의 `parentId`)에서 참조한 공정이 없으면 `REFERENCE_NOT_FOUND`다(HTTP 422, 종료 코드 3, ADR-0006). 계층 전용 '상위 없음' 코드는 두지 않는다.
- 같은 변경 묶음 안에서 지우는 공정을 다른 작업이 참조하면(예: B의 `task.delete`와 B를 잇는 `dependency.add`) `REFERENCE_NOT_FOUND`가 아니라 `VALIDATION_INPUT`이다(종료 코드 3). 같은 대상을 한 묶음에서 겹쳐 다루는 애매한 조합으로 거부하기 때문이다(ADR-0006, 2026-10-08 결정).
- '존재한 적 없음'과 '삭제됨'을 구분하지 않는다. 일관된 결과를 위해서다.

**복구 수단**

- 변경 이력은 후속 검토 대상(F-M08)이므로 잘못 삭제한 공정을 되살리는 수단은 백업뿐이다(N-04, PRD §6.1).
- 휴지통(소프트 삭제)은 후속 검토로 둔다.

**Jira 단계에서 재검토할 것**

- 공정을 물리 삭제하면서 Jira 매핑과 반영 결과(특히 '결과 미확인' 생성 건)까지 지우면, Jira에 고아 이슈가 생겨도 찾을 단서가 사라진다.
- Jira 단계에 들어가기 전에 삭제 표시(tombstone)로 바꿀지, 매핑·반영 결과만 따로 보존할지 다시 검토한다.
- 삭제 표시를 도입해도 API는 `NOT_FOUND`를 유지하는 것을 제안한다. 클라이언트 계약을 바꾸지 않기 위해서다.
- 종속성에 `dep_` ID를 두면 반영 결과를 관계 ID에 묶을 수 있다. 방향을 바꾸면 삭제 + 추가가 되어 새 `dep_`가 생기므로, 옛 반영 결과가 '반영 후 변경됨'임을 알아내기 쉽다(PRD §6.7 검토 제안과 연계).

### 3. 프로젝트 삭제·보관 — 결정(2026-10-08): 삭제는 초기 핵심, 보관은 다음 단계(PRD §13-14)

| 항목 | 결정 |
| --- | --- |
| 초기 핵심 포함 여부 | 결정됨(2026-10-08): 삭제는 초기 핵심, 보관은 다음 단계 |
| 물리 삭제(초기 핵심) | 관리자 권한(ADR-0004), 영향 확인(공정·연결 수, Jira 단계에서는 매핑 수), 명시적 확인(`--yes`)을 거친다. 공정·연결은 CASCADE로 지운다 |
| 보관(다음 단계) | 보관한 프로젝트는 기본 목록에서 숨기고 읽기 전용으로 둔다. 보관 해제를 허용하는 것은 제안이다 |
| 권한 | 결정됨(2026-10-08, ADR-0004 채택): 프로젝트 삭제·보관은 관리자만 한다. 보관 해제 권한은 결정 필요 |
| CLI 동등성 | 보관·보관 해제·삭제 모두 CLI 대상에 포함한다(F-C01). 삭제는 초기 핵심에서, 보관·보관 해제는 보관을 제공하는 단계에서 CLI로도 제공한다. PRD §11은 해당 데이터 기능의 CLI 제공까지 그 단계의 완료 범위로 본다 |

제안 단계 원문(기록): 기본 동작은 '보관(archive). 보관한 프로젝트는 기본 목록에서 숨기고 읽기 전용으로 둔다. 보관 해제를 허용한다'였고, 물리 삭제는 위와 같은 관리자 절차로 함께 두었다. 초기 핵심 포함 여부는 '결정 필요'였다. 결정은 위 표와 같이 관리자 삭제를 초기 핵심에 넣고 보관을 다음 단계로 미뤘다.

### 4. 템플릿 삭제와 출처 — 재사용 단계(F-T09, F-T10, AC-22)

재사용 단계의 범위라 이번 결정에서 다루지 않았다. 아래는 제안으로 두고 재사용 단계에서 확정한다. 템플릿 삭제 권한은 ADR-0004에서 정했다.

- 프로젝트에는 출처를 템플릿 ID, 템플릿 이름, 적용 당시 정의를 식별할 정보(리비전)로 복사해 저장한다. 템플릿 테이블에 대한 외래 키로 묶지 않는다.
- 그래서 템플릿을 삭제해도 프로젝트는 남고 출처를 계속 표시할 수 있다(AC-22). 그 `tpl_` ID를 조회하면 `NOT_FOUND`다.
- 템플릿 삭제는 관리자만 한다(ADR-0004, 2026-10-08 채택).
- 리비전 형식과 수정 이력 보존 방식은 PRD §13-9에서 정한다.
- 템플릿 공정도 포함관계를 가진다. 템플릿 공정의 상위 ID는 같은 템플릿의 `ttk_` ID다. 적용·추출 시 복제 규칙은 §1을 따른다(F-H10).

## 검토한 선택지

### 선택지 A: 타입 접두사 + 전역 불투명 ID만 사용 — 채택

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 낮음. ID 생성 함수 하나와 접두사 검사 |
| 폐쇄망 반입·운영 부담 | 없음. 작은 생성 함수로 충분하고 외부 서비스가 필요 없다 |
| GUI·CLI 동등성(원칙 7) | GUI와 CLI가 같은 문자열을 쓴다(F-C04) |
| 관련 요구사항 적합성 | §7.2(템플릿·실행본 구분), F-T05(새 ID), AC-05(제목 변경 후 유지)를 충족한다. Jira 키와 겹치지 않는다(F-J02) |
| 팀 숙련도 | 확인 필요. 일반적인 방식이라 부담은 작다고 본다 |

장점: 단순하다. 형식만 보고 대상 종류를 알 수 있다. 재사용이 생기지 않는다.

단점: 사람이 손으로 입력하기에는 길다. CLI에서는 복사해 붙이거나 이전 명령의 JSON 출력에서 꺼내 써야 한다.

결정 시점 판단(2026-10-08): 채택했다. 불투명 ID 형식은 ULID다(UUIDv7은 채택하지 않음, §1). 선택 사유는 따로 기록되지 않았다.

### 선택지 B: A + 프로젝트 안 순번 표시키(보조 식별자) — 채택하지 않음(나중에 추가 검토 가능)

| 기준 | 평가 |
| --- | --- |
| 복잡도 | 중간. 프로젝트별 순번 발급(동시성 포함), 표시키 → ID 해석 계층이 필요하다 |
| 폐쇄망 반입·운영 부담 | 없음 |
| GUI·CLI 동등성(원칙 7) | 두 가지 식별자를 모두 받아야 하므로 입력 규칙이 복잡해진다. 출력과 저장은 정식 ID로 통일해야 한다 |
| 관련 요구사항 적합성 | F-P07 사람 검색에 편하다. 다만 템플릿 적용 시 순번을 새로 매겨야 하고(F-T05), 삭제로 생긴 빈 번호를 다시 쓰면 안 된다 |
| 팀 숙련도 | 확인 필요 |

장점: 사람이 화면에서 보고 CLI에 입력하기 쉽다(예: 12번 공정).

단점:

- `#12` 같은 표기는 셸에서 `#` 뒤가 주석으로 처리될 수 있어 따옴표가 필요하다.
- `T-12` 같은 '영문-숫자' 표기는 Jira 이슈 키 꼴과 겹친다.
- 표시키는 프로젝트 안에서만 유일하므로 항상 프로젝트를 함께 지정해야 한다.

제안 단계 서술(기록): 초기에는 선택지 A만 제공하고, B는 사용자 피드백을 받은 뒤 추가 검토하는 것을 제안한다. 나중에 B를 더해도 A의 계약은 깨지지 않는다.

결정 시점 판단(2026-10-08): 처음부터 두지 않는다. 나중에 추가 검토할 수 있다. 선택 사유는 따로 기록되지 않았다.

### 삭제 방식 비교

| 기준 | 물리 삭제 + CASCADE — 채택(초기 핵심) | 삭제 표시(tombstone) — Jira 단계 진입 전 재검토 |
| --- | --- | --- |
| 복잡도 | 낮음 | 중간. 모든 조회에 삭제 제외 조건이 필요하다 |
| 일관성(§7.2) | 외래 키가 보장한다 | 애플리케이션 규칙으로 보장해야 한다 |
| 복구 | 백업뿐 | 되살리기 기능을 만들 수 있다 |
| Jira 매핑 보존 | 함께 사라진다 | 보존할 수 있다 |
| 하위가 있는 공정 | 자손도 CASCADE로 지운다(하위 삭제 (A), 2026-10-08 결정) | 자손에도 삭제 표시가 필요하다 |
| 적합한 시점 | 초기 핵심(Jira 없음) | Jira 단계 진입 전 재검토 |

제안 단계의 열 제목은 '물리 삭제 + CASCADE(초기 제안)'였다(기록).

## 트레이드오프

- 전역 불투명 ID는 견고하지만 사람이 읽고 입력하기 어렵다. GUI 복사 버튼과 CLI JSON 출력으로 보완한다. 순번 표시키(선택지 B)는 처음부터 두지 않으므로 이 불편은 그대로 남는다.
- 물리 삭제는 단순하고 일관성을 DB가 지키지만, 되살리기는 백업으로만 가능하다.
- 재연결을 자동으로 하지 않으면 사용자가 매번 고르는 부담이 있다. 대신 의도하지 않은 연결이 생기지 않는다.
- 초기 핵심에는 프로젝트 보관이 없다. 끝난 프로젝트는 관리자가 지우거나 기본 목록에 그대로 남는다. 보관은 다음 단계에서 제공한다. 제안 단계에서는 '프로젝트 보관을 기본으로 하면 데이터가 계속 쌓인다. 물리 삭제 절차를 함께 둔다'고 적었다(기록).
- 하위까지 삭제하면 구현이 단순한 대신 한 번의 실수로 자손 전체를 잃는다. 미리 보기에 자손 공정과 자손의 연결을 넣고 명시적 확인을 요구해 보완한다. 하위를 올리는 옵션이 없으므로, 하위를 남기려면 삭제 전에 하위를 다른 상위로 옮긴다(`task move`. 연결이 있으면 `--detach` 또는 `graph apply`로 연결 제거와 함께, [ADR-0007](./0007-cli-contract.md)).

- 첫 테이블 스키마와 첫 CLI 명령의 식별자 계약을 확정할 수 있다.
- 템플릿 공정 ID 오용을 형식 검사로 바로 거부할 수 있다.
- 삭제 영향 미리 보기를 변경 묶음 dry-run으로 구현할 수 있다(ADR-0006). 하위가 있는 공정의 미리 보기도 같은 영향 정보로 구현한다.
- 템플릿 복제가 종속성과 포함관계를 같은 ID 매핑으로 다시 잇는다(AC-30).

어려워지는 것:

- 사람이 CLI에 ID를 직접 입력하기 불편하다.
- Jira 단계 진입 전에 삭제 방식을 다시 검토해야 한다.

다시 검토할 시점:

- Jira 선택 연동 단계에 들어가기 전(삭제 표시 여부).
- 사용자들이 CLI 입력 불편을 반복해서 제기할 때(선택지 B).
- 프로젝트 수가 늘어 보관·삭제 정책이 운영 문제가 될 때.

## 남은 확인 사항

채택 시점(2026-10-08)에 아래 사항 중 '결정됨'으로 표시하지 않은 것은 아직 확인·결정되지 않았다. 확인 결과가 이 결정과 맞지 않으면 새 ADR을 써서 이 ADR을 대체한다([README §1](./README.md)).

| 항목 | 확인 대상 |
| --- | --- |
| ULID와 UUIDv7 중 사내 표준이나 선호가 있는지 — 결정됨(2026-10-08): ULID | 사내 아키텍처 담당 |
| ID에 생성 시각이 드러나는 것이 문제가 되는지 | 사내 보안 담당 |
| ULID 표기의 대소문자 — 구현할 때 하나로 고정한다. 입력은 대소문자를 구분하지 않는다 | 개발 참여자 |
| 공정 삭제 시 재연결 제안을 원하는지(PRD §13-15) — 결정됨(2026-10-08): 자동 재연결 없음. 미리 보기에 끊기는 쌍을 보여 주고 사용자가 고른 쌍만 잇는다. CLI는 `--reconnect` | 프로젝트 담당자, 표준 공정 관리 담당자 |
| 프로젝트 보관·삭제를 초기 핵심에 넣을지(PRD §13-14) — 결정됨(2026-10-08): 삭제는 초기 핵심, 보관은 다음 단계 | 프로젝트 담당자 |
| 프로젝트 보관 해제 권한 — 결정 필요 | 프로젝트 담당자 |
| 연결이 있는 공정을 CLI로 삭제할 때 `--yes`를 항상 요구할지 — 결정됨(2026-10-08): 항상 요구한다. 공통 삭제 방식(영향 미리 보기 → 확인 → 물리 삭제)과 ADR-0007 최소 계약 4 채택에 따른다 | 프로젝트 담당자, 에이전트 사용 담당 |
| 하위가 있는 공정을 삭제할 때 하위까지 지울지(A), 한 단계 올릴지(B)(PRD §13-15) — 결정됨(2026-10-08): (A). 올림 옵션은 두지 않는다 | 프로젝트 담당자, 표준 공정 관리 담당자 |
| 삭제 표시(tombstone) 도입 여부 — Jira 단계 진입 전 재검토 | 프로젝트 담당자 |
| 휴지통(소프트 삭제) — 후속 검토 | 프로젝트 담당자 |
