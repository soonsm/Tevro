## 2. 로그인 확장

사용자와 로그인 수단은 나눠 두었다(`users`, `auth_identities`, `src/server/accounts.ts`의 `PasswordProvider`). 로컬 계정이 기본이고 아래를 선택해 붙인다.

- **OIDC:** 표준 하나로 대부분의 계정 서비스를 붙인다. 외부 사용자에게 가장 쓸모가 크다.
- **LDAP:** 설치형 Jira·Confluence가 LDAP이나 Crowd에 연결된 조직이면 같은 계정으로 로그인할 수 있다. 필요한 값은 서버 주소, 조회용 계정, 사용자·그룹 위치(base DN), TLS 인증서다.
- 회원 가입 화면은 두지 않는다. 관리자가 사용자를 만들고, 외부 공급자로 확인된 사람도 Tevro 사용자와 연결돼 있어야 들어온다.

## 3. Jira 연동 (결정 보류)

### 바라는 것

Jira에 들어가지 않고 Tevro 화면에서 Jira 일을 끝낸다. Tevro가 Jira API로 대신 처리한다.

1. 백로그 만들기: Tevro에서 만든 이슈가 Jira 프로젝트 백로그에 들어간다.
2. 스프린트 만들기: Tevro에서 스프린트를 만들고 이슈를 넣는다.
3. 상태 바꾸기: Tevro에서 바꾼 상태가 Jira에 반영된다.

가정: Tevro 공정 하나 = Jira 이슈 하나, 사람마다 자기 Jira 권한(개인 액세스 토큰)으로 실행.

### 기존 원칙과의 충돌

- 'Jira는 선택적 연동'(PRD 원칙 4): 연동은 켜고 끌 수 있게 두어 Jira 없는 팀도 그대로 쓴다.
- '실행 상태는 Tevro가 관리': 상태를 Jira와 맞추려면 어느 쪽이 기준인지, Jira에서 직접 바꾼 내용을 어떻게 가져올지 정해야 한다.

### 정해야 할 것

1. Tevro 상태(미착수·진행 중·완료)와 Jira 워크플로 상태의 짝(설정으로 둘 것)
2. 상하위 공정을 Jira 구조로 옮기는 규칙(큰 공정 = 에픽?)
3. 선후관계를 Jira 이슈 링크(blocks)로도 만들지
4. 스프린트와 Tevro 프로젝트의 관계
5. Jira에서 직접 바꾼 내용을 Tevro로 가져올지(언제, 어떻게)
6. Jira Cloud와 Data Center를 모두 지원할지(API와 인증이 조금 다르다)

제안 순서: 1단계 이슈 만들기·연결과 상태 반영 → 2단계 스프린트 → 3단계 Jira 변경 가져오기. 개발은 무료 Jira Cloud 사이트로 시작할 수 있다.
