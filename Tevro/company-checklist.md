## 1. 사내 계정 로그인 (ADR-0004 선택지 B)

로그인 구조(사용자와 로그인 수단 분리, `PasswordProvider`)는 만들어 두었다. 아래를 알면 해당 방식으로 붙인다.

| 확인할 것 | 답 |
| --- | --- |
| 사내 Jira·Confluence가 무엇으로 로그인하는가: AD/LDAP, SSO(SAML·OIDC), Atlassian Crowd 중 무엇인지 | |
| LDAP이면: 서버 주소, 조회용 계정, 사용자·그룹 위치(base DN), TLS 인증서 | |
| SSO이면: 회사 IdP 이름, Tevro를 앱으로 등록하는 절차와 담당 부서 | |
| 사내망에 Tevro를 올릴 서버가 있는지, HTTPS 인증서는 어떻게 받는지 | |

## 2. Jira 연동 (2026-10-31 논의, 결정 보류)

### 요구사항(결정권자 요청)

Jira에 들어가지 않고 Tevro 화면에서 Jira 일을 끝낸다. Tevro가 Jira API로 대신 처리한다.

1. 백로그 만들기: Tevro에서 만든 이슈가 Jira 프로젝트 백로그에 들어간다.
2. 스프린트 만들기: Tevro에서 스프린트를 만들고 이슈를 넣는다.
3. 상태 바꾸기: Tevro에서 바꾼 상태가 Jira에 반영된다.

작성자가 넣어 읽은 것(확인 필요): Tevro 공정 하나 = Jira 이슈 하나, 대상은 사내 Jira(Data Center), 사람마다 자기 Jira 권한으로 실행.

### 기존 원칙과의 충돌

- 요구사항 원칙 4 'Jira는 선택적 연동': 연동은 켜고 끌 수 있게 두어 Jira 없는 팀도 그대로 쓴다.
- '실행 상태는 Tevro가 관리': 상태를 Jira와 맞추려면 어느 쪽이 기준인지, Jira에서 직접 바꾼 내용을 어떻게 가져올지 정해야 한다.

### 회사에서 확인할 것

| 확인할 것 | 답 |
| --- | --- |
| 사내 Jira 제품과 버전(Jira Software Data Center 몇 버전), 업그레이드·이전 계획 | |
| API 인증 방식: 개인 액세스 토큰(PAT) 허용 여부, OAuth 2.0(들어오는 앱 링크) 등록 가능 여부 | |
| 공용 서비스 계정을 쓸 수 있는지, 사람마다 토큰을 써야 하는지(PRD §6.7, §13-6) | |
| Tevro 서버에서 사내 Jira로 네트워크가 열려 있는지 | |
| 쓸 Jira 프로젝트와 보드(스크럼 보드인지), 이슈 유형(에픽·스토리·작업) | |
| 워크플로 상태 목록과 전환 순서(예: To Do → In Progress → Review → Done) | |
| Jira 관리자 연락처와 협조 가능 여부 | |

### 정해야 할 것(확인 뒤 논의)

1. Tevro 상태(미착수·진행 중·완료)와 Jira 워크플로 상태의 짝
2. 상하위 공정을 Jira 구조로 옮기는 규칙(큰 공정 = 에픽?)
3. 선후관계를 Jira 이슈 링크(blocks)로도 만들지
4. 스프린트와 Tevro 프로젝트의 관계
5. Jira에서 직접 바꾼 내용을 Tevro로 가져올지(언제, 어떻게)

작성자 제안: 1단계 이슈 만들기·연결과 상태 반영 → 2단계 스프린트 → 3단계 Jira 변경 가져오기. 개발은 무료 Jira Cloud 사이트로 시작할 수 있으나 Data Center와 API가 조금 다르므로 사내 Jira에서 확인해야 한다.
